# Visual and Theming Audit

#### When to use this file

Select this file when recon found more than one color scheme (`prefers-color-scheme` rules, a `light-dark()` token layer, a `data-theme` or `class="dark"` switch, a toggle, a pre-paint theme script), a design-token layer or locked palette, shared primitives screens should reuse, a declared icon family, per-tenant brand colors or logos, public pages whose `<head>` matters (a landing reached from a link or QR code, a shared link, an installable web app), a written visual rule such as "nothing generic", "one icon family" or "both themes on every screen", or an approved visual baseline from an earlier run of this skill for the same repository. A CSS framework or icon package in `package.json` is not enough; recon must name the mechanism and files.

Neighbours: WCAG contrast failures present in every theme alike, focus indicators, forced-colors visibility of boundaries and states, and motion are owned by [ACCESSIBILITY.md](ACCESSIBILITY.md) (`ACCESSIBILITY.md#Text and non-text contrast`, `ACCESSIBILITY.md#Forced colors and contrast preference`, `ACCESSIBILITY.md#Motion and timing`); this file asks whether each theme keeps parity, using the same measurements. Geometry is in [RESPONSIVE-AND-LAYOUT.md](RESPONSIVE-AND-LAYOUT.md). Font loading, image weight and theme-switch shift as metrics are in [PERFORMANCE.md](PERFORMANCE.md). `PR-` rows are produced by [PROJECT-CONVENTIONS.md](PROJECT-CONVENTIONS.md); the visual ones are checked here. QR decoding and exports are in [FUNCTIONAL-FLOWS.md](FUNCTIONAL-FLOWS.md) (`FUNCTIONAL-FLOWS.md#Uploads and generated files`); only the QR's appearance per theme is checked here. The rule ids cited in square brackets resolve in [SOURCES.md](SOURCES.md).

## Core discipline (goes into every prompt that uses this file)

```
- A visual finding names its expectation: a confirmed PR- row with a concrete pass criterion, a WCAG criterion, a documented token or primitive, a canonical sibling built on the shared primitive, or an approved baseline capture. "Looks off" or "I would design it differently" is an improvement, never a finding.
- Compare like with like: the same route, viewport, data state and step in light and in dark, recording which of light, dark or system was applied and how (emulated media, stored preference, or both).
- Measure, then look: canvas-normalised computed colors, unrounded contrast ratios, token names traced to source, counts of distinct values, diff ratios. Screenshots illustrate a measured fact; they do not replace it.
- Judgement-against-quote rules (including "Generic or template look") need the row's pass criterion and an independent verifier reaching the same judgement from criterion and artifacts; they stay at low/polish unless the criterion is measurable.
- A pixel difference from a baseline is a lead, never a finding by itself: it needs an approved baseline, matching environment keys, no intended source change that explains it, and a user consequence measured on its own.
- Confirm only what local Chromium shows in the stated theme and context. Real link unfurls, device OS theme behaviour, real Windows contrast themes and non-Chromium native controls go to needs_validation.
- Report your self-assessment honestly; ask a consult instead of guessing outside this lens.
```

## Measurable thresholds used here

- Text contrast: at least 4.5:1, or 3:1 for large text (24 CSS px, or about 18.66 CSS px at weight 700 and above). Ratios are never rounded: 4.499:1 fails. Placeholder, hover and focus text are not exempt; disabled controls, pure decoration and logotypes are [rule: WCAG-01].
- Non-text contrast: at least 3:1 against adjacent colors for boundaries that are a control's only identifying cue, state indicators (check marks, toggle thumbs, selection), focus indicators, and graphics needed to understand content (icons without text, chart series); 2.999:1 fails [rule: WCAG-03].
- Enhanced contrast (7:1 text, 4.5:1 large text) is AAA and advisory: it appears only in improvements unless a confirmed `PR-` row adopts it [rule: WCAG-02].
- Color scheme: the computed `color-scheme` of the root matches the active theme in every capture, and the first screenshot after navigation already shows the final theme's background [rule: TOUCH-32].
- Forced colors: under `forced-colors: active` the theme layer must not fight the system palette (see **Theme parity**) [rule: TOUCH-33].
- Visual regression: per-pixel YIQ threshold 0.2, anti-aliased pixels ignored, per-image budget 0.1 % of pixels (skill default), masked area above 30 % of the viewport marks the comparison low-value (skill default) [rule: E2E-23, E2E-24, E2E-25, E2E-22]. These are the defaults of the config block `visual_regression` (`threshold`, `include_aa`, `max_diff_pixel_ratio`, `max_diff_pixels`, `mask_warn_pct`); a run uses the values its config sets, and the report states them.

## Themes classes (subagent_type: `general`)

**Theme parity**

Check that every screen is complete and readable in both themes with nothing left in the other theme's colors: text or icons that vanish on dark surfaces [rule: WCAG-01]; borders, dividers, focus rings and input outlines that disappear (3:1 when they mark a control boundary or state) [rule: WCAG-03]; shadows as the only separation; charts and badges whose meaning rests on a hue that collapses in dark; dark-ink logos on transparent backgrounds; hard-coded white or black surfaces; links left in the browser's default color on a dark surface; a QR inverted in dark (it must keep dark modules on a light quiet zone, or scanners fail).

Run the unit's matrix (`matrix:core` in standard, `matrix:full` in deep) with `checks.contrast: true` and `checks.structure: true`, configuring `theme.media: true` and `theme.storage` with the app's key so each capture applies both media and stored preference [rule: TOUCH-32]. Compare `contrast.failures[]` between light and dark captures of the same route and viewport; a failure in only one theme is a parity defect, one in both belongs to `ACCESSIBILITY.md#Text and non-text contrast`. Inspect `contrast.manual[]` entries (text over images or gradients) on a crop of `.view.png`, sampling the glyph area rather than trusting computed styles. For separators and outlines, read the border color and adjacent background with an evaluate assertion, canvas-normalise both, and throw with the unrounded ratio when it is below 3:1. When the probe ran axe-core, its color-contrast results are leads in each theme; `incomplete` entries are manual checks, never passes. For a QR, capture its element in both themes and check modules are darker than the quiet zone.

Forced colors as a third rendering: with `media.forcedColors: "active"`, capture the same route in the app's light and dark themes. The browser replaces author colors with system colors, drops box shadows and non-image background gradients, and both captures should therefore converge on the same system palette. A difference between them means a theme rule escaped the system palette: `forced-color-adjust: none` on a themed surface, a hard-coded SVG `fill` or `stroke`, an image used as an icon, or a theme class that sets colors with a selector forced colors does not reach. Report that escape here; whether boundaries, focus and selected states stay visible under forced colors is decided in `ACCESSIBILITY.md#Forced colors and contrast preference` [rule: TOUCH-33]. Chromium's emulation makes the media query match; confirm each claim with computed styles (border and outline widths, `forced-color-adjust`), not with the screenshot alone, and leave how a real Windows contrast theme paints it to `needs_validation`.

Threshold: a core screen unreadable in one theme is high; one low-contrast secondary label in one theme is medium on a core path, low elsewhere; a lost decorative border is polish unless a `PR-` row covers it; a forced-colors escape that hides a control's label or value is medium. OS-scheduled dark mode and vendor "auto dark" for web content are `needs_validation`.

Example (Brasero): `matrix:core;role=owner;data=typical` on `/admin` and `/admin/caja` with a seeded tenant brand colour different from the product default; check `brand-soft`, `on-brand` and `chart-1` in dark against light, and the menu QR from `/admin/ajustes/menu` in both themes.

**Theme initialization and flash**

Check that the first painted frame already uses the final theme (stored preference, or system scheme when nothing is stored); hydration neither flips the theme nor logs a mismatch; the toggle applies at once, persists across reloads and syncs across open tabs; "system" follows a media change while the page is open [rule: TOUCH-32]. The same applies to any other UI state restored before paint (a collapsed sidebar, a density setting). A `color-scheme` meta tag or root property lets the browser paint the canvas in the right scheme before styles load.

The probe captures after load and cannot photograph the first frame, so build evidence from observable facts:

1. **Served HTML.** Read the served `<html>` attributes, the `color-scheme` declaration and the theme script's position: inline, synchronous (no `async`, `defer` or `type=module`), in `<head>` or at the very top of `<body>`, before themed content. Record what the server renders when no preference is known.
2. **Mismatched preference.** Capture with stored preference opposite to emulated media, both ways, at `net=slow3g`. The final `documentElement` must carry the stored theme and `console[]` must hold no hydration warning.
3. **Persistence and sync.** Click the toggle, `goto` the same path, take a `screenshot` step. Then `newTab`, click the toggle in tab 0, and capture tab 1 (`tab: 1`), which must follow without a reload.
4. **System follow.** With nothing stored, run an `emulateMedia` step changing `colorScheme`, then a `screenshot` step.
5. **Switch motion.** With `reducedMotion: true`, toggle the theme and assert that no whole-page color transition runs (computed `transition-duration` on the themed root and main surfaces is 0, or the animation list is empty right after the click). A theme cross-fade that ignores reduced motion is reported here only as theme behaviour; motion as an accessibility failure belongs to `ACCESSIBILITY.md#Motion and timing`.

Threshold: a wrong-theme flash on every load of a core screen is medium; a theme still wrong after hydration, or a toggle that does not persist, is high on core screens; a tab that fails to sync is low; a theme cross-fade under reduced motion is low. When steps 1 and 2 show a render-blocking script placed before content, there is no finding. When source shows it deferred or after themed content but the final state is right, record `needs_validation` with a plan (screen recording on a mid-range phone at `slow3g`, or a frame-by-frame capture). Never claim a flash you did not see.

Example (Brasero): `themeInitScript` and `sidebarInitScript` run before paint and the server renders "light" with `suppressHydrationWarning`. Capture `/admin` with `theme=dark` stored under light media, and with `sidebar=collapsed` at `d1440`; neither theme nor rail may change after hydration.

**Native controls and color scheme**

Check that browser-drawn UI follows the active theme: scrollbars, date and time pickers, `<select>` and its open list, checkboxes, radios, ranges, autofill backgrounds, the `<dialog>` backdrop, and the `theme-color` meta. `color-scheme` must be declared (CSS, a meta tag or `<html>`) and must match a theme the user pinned against the system; native controls must not show light chrome on a dark page [rule: TOUCH-32].

An evaluate assertion compares computed `color-scheme` on `documentElement` and on each form control with the active theme in light, dark and system captures, and throws with the mismatching selectors. Read `structure.head.themeColor` and any `media` variants. Open each native control kind where possible (`click` a `<select>`, focus a date input) and take a `screenshot` step. For enhanced selects (`appearance: base-select`), capture the enhanced rendering and examine the fallback styles other engines get.

Threshold: a native control unreadable in a theme on a core form is medium, high when it hides the selected value of a money or quantity field; a mismatched `theme-color` is polish unless a `PR-` row covers it. Native pickers, autofill and `<select>` popups on iOS, Android, Firefox and WebKit are `needs_validation`, naming engine and control.

Example (Brasero): the `[data-select]` selects on `/admin/inventario/movimientos` and the `Calendar` on `/admin/balance` with `theme=dark`. The viewport sets `colorScheme: "light dark"`; check that a theme pinned through `data-theme` also pins `color-scheme`.

**Per-tenant brand colors**

When tenants or users choose a brand color or logo, every derived color must stay readable in both themes for any value the settings accept, not only the default: text on the brand fill and brand text on surfaces at 4.5:1 [rule: WCAG-01], focus rings and brand-colored control boundaries at 3:1 [rule: WCAG-03], brand-tinted soft backgrounds. The app must clamp, derive or warn when a chosen color cannot meet contrast. Logos must stay visible on the surfaces they sit on, in both themes.

The parent prepares tenants with the product default, the seeded color, and adversarial colors inside the accepted range (a very light one such as `#F5F5F0`, a mid-saturation yellow, a very dark one), through fixtures or the owner's settings inside each agent's own tenant. Capture branded screens in both themes with `checks.contrast: true`, recording tenant and color per capture. Trace the derivation in source (OKLCH lifts, `color-mix`, a computed "on" color) to explain each failure. For logos, crop `.view.png` and check whether source adds a backing plate.

Threshold: an accepted color that makes core text or the primary action unreadable, with no warning, is high. A failure only at an unlikely extreme has reach `narrow`; the default or seeded color failing is `all_users` for that tenant.

Example (Brasero): `brandCssVars` on `<html>` with the product default brand colour, a seeded tenant colour, and the derived `brand-soft`, `brand-ink` and `on-brand` in dark; check the public menu header and the panel sidebar per tenant color.

## Consistency classes (subagent_type: `general`)

**Token discipline**

Check that colors, radii, spacing, type sizes, shadows and z-indexes come from the repository's tokens and that every color token has a value for both themes. Flag, outside token and global CSS files: literal colors (`#…`, `rgb(`, `hsl(`, `oklch(`), palette classes or arbitrary values (`bg-[#…]`, `p-[13px]`, `rounded-[7px]`, `z-[9999]`), inline `style` colors, and text or surface roles whose computed value is identical in both themes.

`scan` components and style modules for those patterns, excluding token files, the theme script, generated files and third-party marks, then confirm each hit renders on a reachable screen. At runtime, an evaluate assertion collects the distinct canvas-normalised `color`, `background-color` and `border-color` per theme and throws with the values that match no token in either theme.

Threshold: backs a finding only through a confirmed `PR-` row or a documented token contract. A literal that breaks a theme on screen is reported under **Theme parity**, with the literal named as its root cause. A token violation with no visible effect is low, as a code-structure convention (see [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md)). Many literals with one cause are one record.

Example (Brasero): `globals.css` locks the palette with `@theme { --color-*: initial; }` and fixes radii at "controls 0.75 rem, panels 1.5 rem, nothing else", so the scan targets arbitrary values, inline styles and other radii, not palette classes.

**Component consistency**

Check that a component looks and behaves the same wherever it appears (primary and secondary buttons, inputs, selects, cards, panels, badges, dialogs, empty states, skeletons) in each state: hover, focus, disabled, pending, error. Outliers such as a 36 px button where the primitive renders 40 px, or a pending state present on one form and absent on another, mean a screen bypassed the shared primitive. The same action carries the same label and the same control variant everywhere, and one label never triggers two different actions [rule: UX-39].

Identify the canonical primitive in source (the shared button, field or card module and its styles): it is the `sibling:` expectation. An evaluate assertion per in-scope screen collects computed `height`, `padding`, `border-radius`, `font-size`, `font-weight` and colors for each instance, plus whether it carries the primitive's marker (a class from its styles module or a `data-` attribute), and throws with the outliers. Build an inventory of action labels with their variant and target across routes and flag label-to-variant or label-to-target divergence [rule: UX-39]. Group by component kind and present outliers as side-by-side crops. Drive states with steps (`hover`, `press` Tab for focus, a submit under `setNetwork` `slow3g` for pending) and take `screenshot` steps.

Threshold: `sibling_screen` is valid only when the sibling is shown canonical (documented, or built on the shared primitive) and the record names the user consequence; capped at `low` unless a figure or task outcome differs, for example a destructive or money action styled as primary on one screen and secondary on another, which is medium [rule: UX-39]. A missing pending or error state belongs to [RESILIENCE-AND-STATES.md](RESILIENCE-AND-STATES.md).

Example (Brasero): the owner's recorded `EmptyState` invitation (brand-colored icon, title, one sentence, primary button); compare the empty `/admin/pedidos`, `/admin/cuentas` and `/admin/balance` (`data=empty`) against it.

**Icon family and imagery**

Check that every icon comes from the declared family at the system's sizes, with no second icon package, no hand-drawn inline `<svg>` duplicating the family, and no emoji used as icons; and that images render correctly, with no broken images, distorted ratios, or leftover placeholder or stock images. Brand marks the family cannot supply are judged against the written rule: a finding only when the confirmed row gives no exception and the owner documented none.

Pass criterion: every element with `role=img` or `aria-hidden=true` that is at most 32 px and not a generated graphic (QR code, chart, brand logo raster) resolves to an import from the family the project declares. Inline `<svg>` is flagged only when it is icon-sized and decorative or serves as a control's label. QR, chart and logo SVGs are listed in the check's `result` and excluded with the reason. Family icons use sizes from the family's documented set unless a confirmed `PR-` row says otherwise; any other size prop, or a CSS override that renders the icon at another size, is a deviation.

`scan` the source roots recon named with `rg -n "<svg"` (excluding test files) to list inline SVG, then sort each hit into icon or generated graphic; search imports for a second family (`lucide`, `react-icons`, `@heroicons`, `@tabler`, `feather` and similar); search icon components for size props outside the set; and look for emoji glyphs in markup text. At runtime an evaluate assertion lists elements with `role=img` or `aria-hidden=true` whose rendered box is at most 32 px, with their size and nearest component, to confirm the static sort. At runtime also read image entries in `failedRequests[]` and `structure.imagesWithoutAlt[]`, and compare each `<img>` rendered ratio with its natural ratio through an evaluate assertion; more than 2 % difference under `object-fit: fill` is distortion.

Threshold: a second family against a confirmed `PR-` row is low, medium when that icon is a control's only label and reads differently from the rest. A broken or distorted image on the public entry or a product card is medium.

Example (Brasero): `CLAUDE.md` says "una sola familia en todo el proyecto, nunca dibujados a mano"; the family is `@primer/octicons-react` with sizes 16 and 24. `src/components/ui/QrCode.tsx` draws a generated QR matrix, not an icon, and is excluded with that reason. `SocialIcon.tsx` is a hand-made brand mark: raise it during `PR-` confirmation and report it only if the owner confirms the rule covers brand marks.

**Generic or template look**

Check only what a confirmed `PR-` row states with a concrete, observable pass criterion; taste is never the criterion. Rows usually become countable facts: gradients in a forbidden hue range, runs of three or more identical cards (same component, size and structure), uppercase eyebrow labels above headings, untouched default chart styling (library palette, gridlines, legend), placeholder copy, emoji decoration.

The extraction step (`research`) quotes the row and its criterion from project-rules.md; a row without a criterion cannot back a unit and becomes an improvement topic. The check (`general`) measures the criterion across the matrix with evaluate assertions that throw with counts: `background-image` gradients with parsed hues, elements with `text-transform: uppercase` directly before an `h1`–`h4`, sibling groups sharing one component and identical computed size, default-palette colors in chart SVG. Attach counts and `.view.png`. The parent strips the hunter's reasoning before Phase 3, and the verifier must reach the same judgement from criterion and artifacts alone; if it disagrees, the record is rejected, not softened.

Threshold: capped at `low` or `polish` unless the criterion is measurable (a count, a token, a size) and the measurement fails. A documented intentional design decision is never a defect.

Example (Brasero): `CLAUDE.md` "Nada genérico": "sin degradados morados, sin filas de tarjetas idénticas, sin etiquetas en mayúsculas sobre cada título, sin iconos ni gráficas por defecto". Each clause becomes a countable criterion in its `PR-` row, checked on the owner dashboard `/admin` at `matrix:core`.

**Public page metadata and share preview**

Check that public and shareable pages render a complete, correct `<head>`: a unique descriptive `<title>` per route and `<html lang>`; meta description; `og:title`, `og:description`, `og:image` and `og:url`; `twitter:card`; favicon and apple-touch icons; a manifest whose name, icons, `theme_color` and `start_url` match the tenant; `theme-color`. Per-tenant pages must show that tenant's name and image, never the product default or another tenant's.

Read `structure.title`, `structure.lang` and `structure.head` (`description`, `og{}`, `twitter{}`, `icons[]`, `manifest`, `themeColor`). Resolve every referenced URL (OG image, icons, manifest) with a GET-only capture on the same loopback origin and read `failedRequests[]` and `blockedRequests[]`. An absolute URL to a non-loopback host is blocked by design: trace how source builds that host (configured base URL or request host); if the deployed value decides the outcome, record `needs_validation`. Compare titles across routes for duplicates.

Threshold: a public entry that previews with another tenant's name or a broken image is medium; a missing description or duplicated title is low; a missing `og:*` set on a page meant for sharing is low, medium when a confirmed `PR-` row requires it. How messaging apps and social networks actually unfurl the link is always `needs_validation`, naming the URL shape, the app to paste it into, and the expected title and image.

Example (Brasero): `/mesa/[slug]`, `/mesa/[slug]/manifest.webmanifest` and `/mesa/[slug]/icono/[size]` for a tenant other than the seed; title, manifest name and icon must be that tenant's and `theme-color` must follow its brand.

## Regression classes (subagent_type: `general`)

**Unintended visual change**

Check, against an approved baseline from an earlier run, that a screen did not change in a way nobody intended and that hurts the user. This class exists only when the run found an approved baseline (`run-metadata.json` `visual_baseline.approved: true`); the parent seeds one unit per `changed` item of `<out>/visual/diff-summary.json`, with the expectation `baseline:<baseline-id>#<capture-key>` (source kind `approved_baseline`) and the context `role=<r>;vp=<vp>;theme=<t>`. An unapproved baseline seeds nothing: its changes are leads in the report only.

Inputs: the diff item (`ratio`, `diffPixels`, `aaPixels`, `regions`, `diffImage`, `maskedAreaPct`, `lowValue`), the baseline and current `.view.png`, the masks applied, and the source diff between the manifest's `source_commit` and the current commit for the files that render that surface plus the `shared_ui_files`. Steps:

1. **Comparable at all.** Only items whose environment keys matched were compared; an `env_mismatch` item is "not comparable", never a regression and never `needs_validation` [rule: E2E-18, TOOLS-40].
2. **Explained or not.** Map each region in `regions` to the element under it (an evaluate assertion on the current page that throws with the selectors at those boxes). When the source diff changed that element or its tokens on purpose (a commit, a `PR-` row or a documented decision says so), mark the unit `covered` with a check that names the commit and the intended change.
3. **Rendering noise first.** Changes confined to text glyphs with unchanged layout point at fonts: read `env.fontsReady` and `env.fontFaceErrors` in both captures before blaming the app [rule: E2E-21]. A large share of anti-aliased pixels with differing pixels under budget is rendering environment drift (more than 1 % of the image, skill default), recorded as a run note, not a finding [rule: E2E-24].
4. **User consequence.** An unexplained change becomes a finding only with a consequence measured on its own: lost or clipped content (`overflow_px`), overlap, text that became unreadable (`contrast_ratio`) or too small (`font_size_px`), a control that shrank below its target (`target_size_px`), broken layout, or a wrong or missing figure. Without one it is an improvement note with the diff image attached.

Measurements: one `visual_diff_ratio` (value = `ratio`, threshold = the run's `maxDiffPixelRatio` as recorded in `diff-summary.json` `options`, which comes from config `max_diff_pixel_ratio`, `pass_if` `<=`, `runs` 1, aggregation `single`) or `visual_diff_pixels`, plus the consequence's own measurement; the profile string names viewport, theme and the first characters of the env key. List every mask in the check's `result`: a regression under a mask is not covered, and an item with `lowValue: true` (masks over `mask_warn_pct` of the viewport, 30 % by default) supports a finding only through a consequence measured outside the masked area [rule: E2E-22].

Threshold: capped at `low` unless a figure or task outcome differs (the record then carries a non-diff measurement, or a condition of kind `data_state`, `app_configuration`, `user_role` or `concurrency`); a change that hides a primary action or a money figure on a core path is high. An `unstable` item (the screen never settled) is not a diff finding: it is a lead for `ACCESSIBILITY.md#Motion and timing` or `RESILIENCE-AND-STATES.md#Loading states` (an endless spinner, an animation that ignores freezing) [rule: E2E-19].

Example (Brasero): a baseline of `/mesa/audit-ready` at m390 in light and dark; a later run shows the product grid shifted down by a new banner. The diff alone proves nothing; the finding needs the source diff to show the banner was not meant for that page and a measurement that the first product card fell below the fold or that the banner overlaps the cart button.

## Visual baselines between runs (parent procedure)

The parent runs this procedure; agents receive only its outputs. Baselines live at `<output_root>/<repo>/baselines/<baseline-id>/` (a `manifest.json` and `captures/<routeId>/<viewportId>.<theme>.view.png`), outside the skill directory and the target repository, and are never committed.

1. **Find a baseline (Phase 1).** When the config sets `visual_regression.enabled: false`, skip this whole procedure: no sweep, no compare, no unit of **Unintended visual change**, and `run-metadata.json` `visual_baseline` gets a null id and the note "visual regression disabled in config". Otherwise pick the latest approved baseline of the repository whose environment can match this run: same platform, driver, headless mode and browser major version. Record it in `run-metadata.json` `visual_baseline`. An unapproved comparable baseline is still compared, for leads only. With none at all, the sweep still runs so the run can be promoted, no unit of **Unintended visual change** is seeded, the gap is recorded as `visual_baseline_unavailable`, and a REPORT line says so.
2. **Sweep with the baseline's settings (Phase 2, wave 1).** Write `tools/visual-sweep.json`: the baseline's routes × viewports × themes, `stableShots` on, the baseline's masks as `routes[].mask`, no steps beyond waits, and the same `clock.now`, `timezone` and `locale` as the baseline so dates and number formats cannot differ [rule: E2E-09, E2E-10]. The parent runs the probe itself when every swept route is reachable without a login or fixture step; otherwise one `w1-sweep` agent (haiku) runs it. Either way the sweep counts as browser-driving for the wave.
3. **What the probe does before each view screenshot.** It brings the page and the visual viewport back to the scroll origin when a step left them panned (unless a `scroll` step asked for the position; `measuredState.scrollReset`), freezes animations and transitions, hides the text caret, moves the pointer outside the viewport, hides the overlay scrollbars of mobile viewports, which otherwise fade between two shots (`screenshots.scrollbarsHidden`), awaits `document.fonts.ready` (5 s) and records failed font faces, overlays masks in `#FF00FF`, then takes viewport screenshots until two consecutive ones are byte-identical or `stableShots.maxAttempts` is reached, recording `screenshots.viewStable` [rule: E2E-19, E2E-20, E2E-21, E2E-22]. Captures are at CSS scale with the viewport's DPR, which is part of the key [rule: E2E-26]. Each capture's `env` block hashes platform, driver, browser major version, headless mode, viewport with DPR, theme, color scheme, reduced motion, forced colors, locale, time zone and the launch arguments into `envKey`; a different launch flag set (font hinting, color profile) gives a different key [rule: E2E-18, E2E-28]. Reduced-motion or forced-colors captures therefore compare only with baselines taken the same way.
4. **Compare (no agent).** `node <skill-dir>/scripts/ui-diff.mjs --baseline <baseline-dir> --current <sweep-out-dir> --out <out>/visual --threshold <threshold> --max-diff-pixel-ratio <max_diff_pixel_ratio> [--max-diff-pixels <max_diff_pixels>] [--include-aa] --mask-warn-pct <mask_warn_pct>`, every value taken from the config block `visual_regression`: pass `--max-diff-pixels` only when `max_diff_pixels` is a number (null leaves the ratio as the only budget) and `--include-aa` only when `include_aa` is true. With no config value the script's own defaults apply: threshold 0.2, anti-aliasing ignored, ratio 0.001, mask warning at 30 %. All path arguments are absolute (expand `~` first); the script refuses relative ones. The script decodes PNGs in plain Node and compares pixels with the YIQ perceptual distance (a pixel differs when its weighted squared difference exceeds 35215 × threshold²) and an anti-aliasing detector; the budget is the smaller of the limits set, a size mismatch never fits a budget, and it lists up to 20 differing regions [rule: E2E-23, E2E-24, E2E-25, E2E-31]. Decoding in a page canvas was considered and rejected because color management and premultiplied alpha make canvas readback inexact [rule: E2E-29, E2E-30, E2E-32]. The comparator's self-test runs first; exit 3 means the diff is disabled for this run and the report says why. Exit 4 only means at least one item is `changed` or `size_mismatch`; it is the normal "there is something to look at" result.
5. **Read the statuses.** `unchanged` and `within_budget` are coverage; `changed` seeds a unit when the baseline is approved; `size_mismatch` (usually a page height change) and every change against an unapproved baseline are listed in COVERAGE.md "Visual changes since baseline" as leads; `env_mismatch` is "not comparable"; `missing_baseline` and `missing_current` are coverage gaps; `unstable` is a lead for the motion or loading classes; `lowValue` items are marked low-value; an item with `currentFailed: true` comes from a capture whose steps failed, so it does not show the state its key names and is never read as a regression. A `within_budget` item whose differing pixels form one or two compact regions is listed in COVERAGE.md "Visual changes since baseline" as a lead: a heading recoloured with a letter-spacing change can stay under a 0.1 % budget at desktop size.
6. **Promote and approve only on the owner's word (Phase 6).** A changed screenshot is never accepted silently [rule: E2E-27]. The parent offers once, in the report language, to save this run's sweep as the new baseline and whether to approve it. Pass `--baseline-root` as an absolute path: expand a leading `~` of `output_root` to the home directory first, because the script refuses a relative or `~`-prefixed root. Only an explicit yes runs `ui-diff.mjs --promote --from <sweep-out-dir> --baseline-root <output_root>/<repo>/baselines --baseline-id <run-id> --repo <repo> --source-commit <sha>`, and only an explicit approval runs `ui-diff.mjs --approve --baseline-root <same> --baseline-id <run-id> --approved-text-file <out>/tools/<file>`, where the file holds the owner's words verbatim. `--promote` leaves out every capture whose steps failed (its `skipped` list names them with `capture_failed`) and keeps unstable ones with `viewStable: false`, so a later compare reports them as `unstable` rather than as changes. An unapproved baseline produces leads only and is never an expectation source.

## Universal moves (they cut across every class above)

- Pair every capture with its twin in the other theme (same route, viewport, data state and step). The check's `variant` records only `theme=<light|dark|system>` plus `vp`; how the theme was applied (emulated media, stored preference, or both) goes in the check's `result` text and is visible in the capture JSON (`media`, `theme`, `env`), never in `variant`. A difference in only one of the pair is the finding; one present in both belongs to another class.
- Trace each defect from the rendered value back to the token, primitive or literal that produced it, and propose the smallest fix at that origin (one token pair, one primitive, one derivation), never per-screen overrides. The regression check is a probe config re-running both themes, and, once the fix is approved, a new baseline the owner approves.
- Read project-rules.md and the documented decisions before calling anything inconsistent or generic. An approved color, an owner-fixed position or a stated exception is never a defect; record it in `positive_patterns` when applied consistently.
- Cite rules in the expectation as `RULE:<id>` for `standard` and `platform_contract` sources (for example `RULE:TOUCH-32`); use `WCAG22#<criterion>` for a WCAG criterion.

## Validation rules (checked before any finding from this file is reported)

1. Cite the expectation exactly: the `PR-` row with its pass criterion, the WCAG criterion, the token or primitive file:line, the `sibling:` path with proof it is canonical, or the approved baseline capture. Without one of these, it is an improvement.
2. Show the measurement for both themes, or for every tenant color involved: canvas-normalised colors, unrounded ratios, counts or sizes, each with threshold and `pass_if`. A value meeting its own threshold is not a finding, and a screenshot or diff image without a measurement confirms nothing.
3. Rule out fixture and capture artifacts: polling or a carousel mid-transition, a theme applied only through media when the app reads storage (or the reverse), a brand color outside the range the settings accept, dev-only overlays, fonts that failed to load, a frozen clock that differs from the baseline's.
4. Respect the caps: `sibling_screen` and `approved_baseline` records stay at `low` unless a figure or task outcome differs; judgement-against-quote records (including **Generic or template look**) stay at `low`/`polish` unless the criterion is measurable and an independent verifier reproduced the judgement without the hunter's reasoning; AAA contrast stays in improvements unless a `PR-` row adopts it [rule: WCAG-02].
5. An environment mismatch between baseline and run is "not comparable": never a finding and never `needs_validation`. An **Unintended visual change** record carries a `visual_diff_ratio` or `visual_diff_pixels` measurement and names the source change it checked.
6. Use `confirmed` only when the hunter and then an independent verifier reproduced the deviation in local Chromium, in the stated theme, viewport and tenant, with promoted captures. Use `needs_validation` when the decisive fact needs another engine's native controls, a real device's OS theme behaviour, a real Windows contrast theme, a first-frame recording the probe cannot take, a deployed base URL, or a real third-party unfurl, naming the device, app or engine and what to look for.
