# Functional Flows Audit

#### When to use this file

Select this file when recon (1a and 1b in [RECONNAISSANCE.md](RECONNAISSANCE.md)) found at least one of these:

- an entity that moves through named states, such as an order, booking, ticket, invoice or shift;
- a flow that spans several screens, dialogs or steps;
- a figure (money, quantity, count, time) shown on more than one screen, or exported to a file;
- forms that create or change records;
- actions that delete, cancel, refund, close or otherwise cannot be taken back by simply doing the opposite;
- lists with search, filters, sorting or pagination;
- uploads, or files the app generates (spreadsheets, PDFs, QR codes);
- actions that only some roles may take.

A package name alone, such as a form library, does not select this file. The surface has to exist.

Neighbouring files: [RESILIENCE-AND-STATES.md](RESILIENCE-AND-STATES.md) owns what a screen does while loading, failing, offline or after the session ends, and how fast feedback appears. This file owns whether the flow produces the right result. [ACCESSIBILITY.md](ACCESSIBILITY.md) owns labels, the programmatic link between a field and its error, and whether messages are announced; this file owns which values are accepted, what the message says, and what gets saved. [PROJECT-CONVENTIONS.md](PROJECT-CONVENTIONS.md) turns written business rules into `PR-` rows that units here can cite. Ordinary lenses in [LENSES.md](LENSES.md) (**Functional flows**, **Business rules as displayed**, **Forms and validation**) are the breadth versions of the classes below; use the classes when recon justified depth.

Routing: the five classes `Displayed business rules`, `Figure consistency across screens`, `Money, quantity and rounding`, `Time, dates and time zones` and `Exports match the screen` are business lenses. Their hunter groups run as task kind `hunt_business` and their verifiers on the strong verification kinds (see [ORCHESTRATION.md](ORCHESTRATION.md)). Every other class here runs as `hunt_standard` unless a unit cites a judgement-against-quote `PR-` row.

#### Heuristics as checks

Usability heuristics are judgement aids, not laws. This file uses them only through rules that are true or false on a concrete screen, each with a threshold and a check, listed in [SOURCES.md](SOURCES.md) under the `UX-` ids. Four consequences for every unit here:

- A finding names the rule id and the measured value next to the threshold. A heuristic named without a measurement ("this feels confusing") is not a candidate; it may be an improvement at most.
- Rules that need wording judgement (whether an error message tells the user what to do, whether a hint is needed) leave `needs_validation` only after two independent agents agree or a judge decides [rule: UX-11, UX-42].
- Numbers that come from e-commerce benchmarks (field counts, abandonment rates) explain why a rule exists; they are not thresholds for every app. A finding built on one is an improvement unless a confirmed `PR-` row adopts it [rule: UX-18, UX-19].
- Thresholds this skill chose itself (the 50 ms double-click gap, the "about one field height" error distance) are labelled as skill thresholds in the record, never as quoted standards.

## Core discipline (goes into every prompt that uses this file)

```
- Judge outcomes, not appearances. A flow defect is a wrong record, a wrong figure, a lost input, an illegal transition that went through, a destructive action that ran without the guard the rule requires, or a legal transition the UI refused. Check the result where it lands: the other screen, the list, the export, or the read-only row count.
- Name the rule before testing it. Every expectation cites a business-rule source (code path with anchor, product document, confirmed PR- row), a RULE: id from SOURCES.md, or a canonical sibling screen. "It would be nicer if" is not an expectation.
- Work only in your own tenant and on your own fixture data. Record every record you create, change, delete or consume in fixture_effects, and never touch global settings, seed, reset or another tenant's data.
- Stop at the smallest action that shows the deviation. One duplicated order proves double submit; ten do not prove it better and burn throttles shared by every agent on the loopback address.
- Wait on conditions, not on time: waitFor a selector or text with a deadline; use wait only for an interval you are measuring (a polling period, an undo window) and say so.
- Compare figures as numbers, never as strings: parse with the locale, normalise no-break spaces, then compare.
- Use confirmed only when you reproduced the wrong outcome locally in the stated context with promoted evidence. Use needs_validation when the decisive fact is a real server clock crossing a boundary, production data volume, a real device, or a third party.
- Report your self-assessment honestly; ask a consult instead of guessing outside this lens.
```

## Flow and state classes (subagent_type: `general`)

**Entity lifecycle transitions**
Build the state table for each entity recon listed: every state, every transition, who may trigger it, and what it changes (stock, money, other entities, audit entries). Then, for each state, try every action the UI offers in that state, plus every action still reachable through a deep link, a stale button in a second tab (`newTab`), or a dialog opened before the state changed. A legal transition must succeed and update every screen that shows the entity; an illegal one must be refused with a message that says why, and must leave nothing half-written. Reproduce with probe `click`/`fill` steps on the owning persona's saved session, then confirm the landing state on a second route capture. Transitions driven only by the server clock (expiry, "late" flags) are tested with seeded boundary data, never by waiting real hours. A status shown to the user as a raw code value (an enum literal, an all-caps token, `null`) instead of the domain word is a finding of its own [rule: UX-38].
Example (Brasero): an order that is already CANCELADO must not offer "Validar pago"; a booking request SOLICITADA that crossed its 60-minute open-hours expiry must not be acceptable from a stale booking-board tab.

**Multi-step flows and drafts**
Walk each flow end to end in its intended order, then out of order: skip a step through its URL, return to an earlier step, change a choice made earlier, and close and reopen the dialog. Checks, each true or false:
- Data the user already entered or was given in the same process is filled in or offered as a choice when a later step needs it again; browser autofill does not count. Exceptions: re-entry that is essential, a security confirmation (a new password typed twice), or a value that is no longer valid [rule: WCAG-29, UX-22].
- Changing an earlier choice updates everything that depends on it, or says what it will reset before it does.
- Every step has a visible way out (Cancel, Close or Back) that does not require finishing the flow, and browser Back from any step leaves the step [rule: UX-31].
- Changing a select, radio, checkbox or text field does not by itself submit, navigate or open a window unless the user was told beforehand; a filter that updates a list in place is not a change of context [rule: UX-23].
- On a flow that commits money or a booking, the final amount (fees, deposits, taxes included) is shown before the committing step and equals the amount recorded, compared in minor units on the confirmation screen [rule: UX-20].
A flow that silently drops a cart, form contents or a selection is a defect only when the user had no warning and no way back; how leaving with unsaved work is guarded is checked under `Destructive actions, confirmation and undo`.
Example (Brasero): GuestForm on `/mesa/[slug]` followed by "¿Eres tú?" for a returning phone must not ask again for the name already given; picking a different terrace table after filling the cart must not change prices or empty the cart without saying so.

**Double submit and idempotent actions**
For every action that creates, pays, confirms or closes something, try three things: two `click` steps in a row on the same control (the probe pauses about 50 ms after each click, so the second lands inside the pending window; the 50 ms gap is a skill threshold), `press` Enter twice on the focused submit control, and a second `click` while the first request is pending under `setNetwork` `slow3g`. The rule is that a repeat activation inside the pending window adds zero mutating operations [rule: UX-07]. Judge the outcome, not the look: exactly one record, one stock movement and one cash movement, verified with the read-only `count_command` before and after, recorded as a `test` check whose output file is the artifact. Whether the control shows a busy state is checked by `RESILIENCE-AND-STATES.md#Slow responses and pending feedback`; here, a missing busy state is only context. If your assignment does not grant `count_command`, compare the resulting list on a second capture and say in `unresolved` that the database count was not taken; a list that shows two rows is enough for `confirmed`, a list that shows one is not enough for `covered` on a money action. A duplicate that appears in only some reruns is still a product race when the probe's click landed on a stable control that was the hit target; follow the intermittent-results procedure in [HUNTING.md](HUNTING.md) and record the class [rule: E2E-04, E2E-15, E2E-16].
Example (Brasero): CheckoutDialog "Enviar pedido" twice must leave one PedidoItem set, one VENTA movement per item, and one entry on the tab.

**Concurrent sessions and stale views**
Use `session=twotabs` (one persona, `newTab`, steps addressed with `tab: 0|1`) and `session=twousers` (two personas of the same tenant, two probe runs with separate `--out` directories, the acting run started while the observing run sits in a `wait` step; record both `startedAt` values). Cover: the same entity edited in both places; the last unit of stock taken by two buyers; a price or availability change while the item is in a cart; an entity deleted or deactivated while another screen still offers it. Expected: no negative stock, no order at a price neither screen showed, a clear message to the loser of a race, and both screens converging within one polling interval. Silent last-write-wins is a defect only when the overwritten user is told it saved. Two-run timing is the classic source of intermittent results; rerun before reporting and classify a non-reproducing result rather than dropping it [rule: E2E-15, E2E-16].
Example (Brasero): two customers on `/mesa/[slug]` with the last unit in the cart; the second must get the "quedan N" choice, and Inventario must show stock 0, not −1.

**Live updates and polling correctness**
List each screen that refreshes itself and its interval from recon 1b. Check correctness, not cost (cost belongs to [PERFORMANCE.md](PERFORMANCE.md)): a change made by the other persona appears within one interval plus settle time; a refresh does not reset an open dialog, a half-typed field, scroll position or the current filter; counters, badges and the list they summarise agree after every refresh; arrival alerts fire once per new item, not once per poll. Reproduce with a `twousers` pair: the observer holds a dialog open with typed text across at least two intervals (`wait` steps, labelled as measured intervals [rule: E2E-01]), the actor creates an item, and the observer takes `screenshot` steps before and after. Freeze or wait out polling before any capture used as visual evidence.
Example (Brasero): an order arriving while EditOrderDialog is open on `/admin/pedidos` (5 s refresh) must not close the dialog or lose the edited quantity, and the bell count must equal the board.

## Rules and figures classes (subagent_type: `general`)

**Displayed business rules**
For each rule recon traced to its enforcing code, check that the screen tells the truth about it: what the UI allows matches what the server accepts, messages state the actual limit, and disabled controls say why. Test both sides: the UI must not offer what the server will refuse, and must not hide what the rule permits. A primary action that is disabled until a condition is met must say, in visible text near it, what is missing; otherwise it stays enabled and the submit reports the problem [rule: UX-26]. A rule enforced only on the client is an outcome defect when a second path (a stale tab, a deep link) gets around it; report the visible part here and refer the rest to the project's security review (for example a security-audit skill).
Example (Brasero): "No se vende lo que no hay" means an out-of-stock item shows "No hay existencias" and cannot be added; "el turno no se cierra con saldos pendientes" means the close action on `/admin/caja` explains which tabs are blocking; regulars (ClienteFrecuente) are never shown a deposit on `/mesa/[slug]/reservas`.

**Figure consistency across screens**
Pick one scenario in your tenant and write down every figure it produces on every screen that shows it, with route, label and value. The figures must agree to the smallest unit and must come from one rule. Expected relationships to verify: the lines add up to the subtotal; subtotal plus or minus adjustments equals the total; the total shown before commitment equals the total recorded [rule: UX-20]; expected cash equals opening cash plus cash sales minus cash expenses; separately tracked money is never folded into another total. Read each figure from the screen and parse it with the locale before comparing (see `Locale and number formatting`); two strings that differ only in a no-break space are the same figure. Report one record per root cause with the other screens in `also_affects`. A cross-screen difference is `high` per [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md); a figure that is wrong everywhere in the same way is a business-rule defect, not a consistency one. When the cause cannot be settled at the tier you run on, say so with `needs_stronger_model` in your self-assessment instead of guessing.
Example (Brasero): after a partial payment, the tab on `/admin/cuentas`, the TillTape on `/admin/caja`, "vendido" on `/admin`, `/admin/balance` and the Excel export must agree, and booking money must stay in its own block, never in "vendido", expected cash or "Quedó".

**Money, quantity and rounding**
Check that every displayed amount comes from one formatter configured with an explicit locale and an explicit ISO 4217 currency, with the number of fraction digits the currency or a single documented project rule sets [rule: UX-34]. Then check the arithmetic: a client-side computation equals the server's (compare the cart total with the saved order), discounts and promotions round the same way everywhere, and quantity limits hold at 0, 1, the maximum and maximum plus one. Measurable failures: a floating-point artefact on screen (`0.30000000000000004`, or more fraction digits than the currency uses); a fractional amount in a currency the project shows without decimals; in display code, `toFixed(` or a hard-coded currency symbol glued to a number, or `toLocaleString()` with no arguments. Use a `typical` fixture plus one built for the edge (a 7- to 9-digit total, a 999 quantity, a discount that does not divide evenly).
Example (Brasero): COP is shown without decimals, so a `,5` or `.50` anywhere, or a discounted line whose total differs between the cart and PedidoItem, is a finding.

**Time, dates and time zones**
Find every place where a date decides something: "today" filters, daily totals, shifts and bookings that cross midnight, validity windows, expiries, relative times. User-facing dates come from a locale-aware formatter with an explicit time zone chosen by a documented rule (the business's or the user's); a formatter call with no `timeZone` in server-rendered code is a lead, and the same instant shown as two different calendar dates on two screens is a finding [rule: UX-35]. Where the audience is mixed or the date leaves the app (an export, a printed ticket), an all-numeric date that reads differently in two locales is a lead for a month name or ISO 8601 [rule: UX-35]. Times use one hour cycle per locale across the app; `14:00` on one screen and `2:00 PM` on another for the same locale is a low-impact finding [rule: UX-36].
Test the client side with `clock.now` (init-script shift) at just before and just after each boundary, and `timezone` both at `clock.timezone` and at a zone far from it such as `Asia/Tokyo` (`tz=Asia/Tokyo`), to catch code that assumes the server and client share a zone. Test the server side only with `seeded-boundaries` fixtures placed around real server time; there is no server faketime. A claim that needs the real server clock to cross a boundary is `needs_validation`.
Pin the server's own zone as well, so that results do not depend on the machine. The server process runs with `TZ=UTC`, or with the deployment's documented TZ when there is one, and the parent records it as `clock.server_process_tz`. Hosting platforms usually run in UTC, while a developer machine, VM or WSL distribution often runs in a local zone. Recon lists every date computation that names no explicit zone, such as `new Date().getDate()`, `toDateString()` or `setHours(0,0,0,0)` with no zone argument, or a `toLocaleDateString` call with no `timeZone`. Each one becomes a variant unit: its expectation ref is that helper (`path#anchor`), its context carries `tz=<clock.timezone>`, and its `server_process_tz` bookkeeping field holds the business zone. The parent runs these units with the server restarted under the business zone. Only the parent restarts the server, and only between waves, never mid-wave. Those units form the server-zone wave, which runs after the ordinary waves and before the performance wave (wave order in [HUNTING.md](HUNTING.md)); the server returns to the recorded TZ afterwards. Every check result in that wave states the server TZ it ran under. A figure that changes between the two server zones is the finding.
Example (Brasero): `src/lib/cash/offers.ts` computes the day with the restaurant's `zonaHoraria`, falling back to America/Bogota, so it needs no variant; any helper that does not do this is the lead. A shift opened at 22:00 belongs to the day it opened, even after midnight. A booking hour after 24:00 (closing past 1440 minutes) must appear on the restaurant day, on both the booking board and the customer page.

**Locale and number formatting**
Every visible amount, date, time and count uses the locale the repository chose, consistently: currency symbol and grouping, no line break between symbol and digits, local date order, one hour cycle, accents preserved, and correct singular and plural forms (an `Intl.PluralRules` category, not a hard-coded "s"). The same amount renders identically on every screen [rule: UX-34]. How to compare without false positives:
- Never compare a formatted string with a literal written in the unit. Formatter output depends on the ICU and CLDR version of the runtime, so two correct engines can differ in spacing or even in fraction digits [rule: UX-34].
- In an `evaluate` assertion, rebuild the expected text with `Intl.NumberFormat(locale, {style: "currency", currency}).formatToParts(value)` or parse both sides to numbers, and replace U+00A0 (no-break space) and U+202F (narrow no-break space) with a plain space on both sides before any string comparison.
- Two different formats for the same currency on two screens, or a server-rendered amount that changes format after hydration, is the finding; a hard-coded format is a defect only when it disagrees on screen with the `Intl` output used elsewhere.
- Untranslated keys, template braces or raw values on screen (`foo.bar.baz`, `{{name}}`, `undefined`, `NaN`, `Invalid Date`, `[object Object]`) are findings; collect candidates from the capture's `structure.badText` and from screenshots at m320, where wrapping shows [rule: UX-33].
Example (Brasero): COP amounts in the repository's chosen format (es-CO groups with dots), es-CO dates, and "ñ" intact in restaurant and product names.

**Exports match the screen**
For each generated download, apply the same filters on screen and in the export and compare: same rows, same totals, same date range edges, same rounding, same labels. This is a `browser` check, and the file is read inside the browser so that no cookie ever leaves it. Clicking the download link does nothing useful, because the probe denies downloads. Instead, on the owning persona's saved session, `goto` the screen with the filters applied, then add one `evaluate` step written as an assertion. Its expression (an async function called at once, so the probe awaits it) does a same-origin GET `fetch` of the exact export URL that the screen's link points to, with no body, no other method and no extra headers; decodes the file in the page; reads the screen's figures for the same filters from the DOM; and throws a short error naming the first difference (for example `rows 41 vs 42` or `total Card 12000 vs 12500`) when anything differs. The probe records the expression verbatim and whether it threw, with the error text clipped to 300 characters, and never the returned value; so the comparison must happen inside the expression, a passing step is the evidence of agreement, and a failing step's message is the measurement. An `.xlsx` is a zip of XML parts: Chromium's `DecompressionStream('deflate-raw')` inflates them and `DOMParser` reads the sheet and shared-strings XML. Parse numbers on both sides as in `Locale and number formatting`. The capture JSON is the check's artifact, so a verifier can rerun the same expression. Never save the file to `scratch/` or run a shell download, and never ask the parent for a mid-run fetch: a hunter cannot request one, and the parent does not pre-fetch exports. If the export is produced only by a POST, a server action or a format the page cannot decode, or if the decoder and comparison do not fit the probe's 4,000-character expression limit, mark the unit `blocked` and name the missing export read in `unresolved`.
Example (Brasero): `/admin/balance/excel?desde=…&hasta=…` (a GET route gated by `requirePermiso("verBalance")`, so it runs on the owner session) for a range that contains an after-midnight shift must give the same per-category and per-method totals as `/admin/balance` with the same `desde`/`hasta`; the product README states that the Excel matches what the screen shows.

## Input, lists and files classes (subagent_type: `general`)

**Form validation and boundary values**
For every input, try: empty, whitespace only, 0, 1, the maximum, the maximum plus one, negative, a decimal where integers are expected, a very large number, leading zeros, pasted separators (`1.000`, `1,000`, `$ 1.000`), more than 255 characters, accents and emoji, and HTML-looking text (`<b>x</b>` must render as text). Expected: no crash, the server refusing the same value (resubmit it through a second path such as an edit form), and the saved value equal to the shown value. A value the client rejects but the server would accept is not a finding by itself; a value the client accepts and the server silently changes is. Then check what the user is told, rule by rule:
- A rejected field is identified and the problem described in text, not by colour or an icon alone [rule: WCAG-28, UX-08]. The programmatic link (`aria-invalid`, `aria-describedby`) and its announcement belong to `ACCESSIBILITY.md#Form labels, errors and help`; record what you saw and leave the verdict there.
- The message sits next to its field, not only in a toast or a banner at the top (skill tolerance: inside the field's group, or within about one field height) [rule: UX-09]. On a multi-field form, a failed submit moves focus to the first invalid field or to a summary that links to each field, with the same wording as the inline messages [rule: UX-10].
- Two different causes on one field (empty, too short, wrong format, out of range) do not produce the same message, and no message is only a generic phrase ("invalid", "an error occurred", "something went wrong") or a raw code or status [rule: UX-11]. Sign-in and password-reset forms may use one message on purpose to avoid revealing accounts; that is not a finding [rule: UX-11]. Whether a specific message also says how to fix the problem is a wording judgement and needs a second agent [rule: UX-11].
- Blaming or alarming words in error copy are reported as `low` or below, never higher [rule: UX-12].
- After a failed submit, every non-secret field keeps what the user typed, the valid fields included; password and card security fields may be cleared [rule: UX-13].
- No error appears while the user is still typing a field's first value (fields of fixed length may validate when full), and a shown error clears as soon as the value becomes valid. Validating on leaving the field versus only on submit is a project convention, not a defect [rule: UX-14].
- Every required field is marked, or every optional field is, applied the same way across the app, and the mark matches `required`/`aria-required`; a field the server requires but the UI does not mark is found by submitting empty [rule: UX-17]. Login forms are exempt [rule: UX-17].
- Personal-data fields carry a valid `autocomplete` token and numeric, phone and email fields bring up the matching keyboard (`type` or `inputmode`) [rule: UX-15]; each input has a visible label outside it, not a placeholder alone [rule: UX-16]. Report both as leads to the accessibility lens when it is not in your assignment.
- Typed dates accept common separators and missing leading zeros in the locale's order, and phone fields accept spaces and dashes [rule: UX-24].
- In a locale whose decimal separator is a comma, typing `1.500` and `1,5` into an amount field either gives the value the locale means or shows a visible error; a value silently stored with the other reading is money corruption and is at least `high` [rule: UX-37].
- No reset or clear-all control sits in the action row next to submit [rule: UX-25].
- On a checkout-like flow, count the visible fields per step and trace each to the code that consumes it; a field no server handler reads is a finding, a high count alone is an improvement [rule: UX-18].
Example (Brasero): GuestForm name 2–40 characters and phone 7–15 digits (try `300 123 4567` and `3001234567`); ProductForm price with pasted `$ 12.000`.

**Search, filter, sort and pagination**
Check: the no-results state, which must read differently from a list that is truly empty and from one still loading, and must offer clearing the filter [rule: UX-40]; special characters and accents in the query (searching with and without diacritics as the rule says); filters combined with pagination (page 3 of a filter must not show unfiltered rows); sort stability across pages; filter state reflected in the URL so a refresh or shared link reproduces the view; and clearing filters returning the full list. Use `heavy` data for pagination and `empty` for the no-results state. A search box that changes the list while the user types, under `slow3g`, must end on the results for the final query, not for an earlier one that answered late.
Example (Brasero): `/admin/auditoria` with tag, person and date filters combined, then refreshed; `/admin/inventario/movimientos` with filters in the query string; searching "pina" versus "piña".

**Uploads and generated files**
Upload only local dummy files that live inside the probe config's directory (`upload` step). Check that size and type limits are stated before the upload, enforced with a clear message (oversized and wrong-type files), and that the stored result is what the user picked (orientation, crop, the right record). An upload that takes longer than 10 s under the throttled profile shows percent-done or a count and can be cancelled; that part is judged under `RESILIENCE-AND-STATES.md#Slow responses and pending feedback` [rule: UX-03, UX-04]. For generated images, decode the output: a QR image must decode to the expected loopback-relative URL path for the right tenant. Never upload to external storage and never follow the decoded link off loopback.
Example (Brasero): a 5 MB product photo against the 6 MB server-action body limit on `/admin/inventario/nuevo`; the printable QR on `/admin/ajustes/menu` must decode to `/mesa/<slug>`.

**Role-gated actions**
Build a role × route × action grid from recon 1b. For each role: navigation shows only reachable sections; actions the role lacks are hidden or explained, never offered and then failed with a raw error; a direct URL to a gated screen lands on a designed redirect or forbidden state. Report a visible-but-forbidden control or a raw error page as a UX defect here and refer the access question to the project's security review; never attempt to get around the gate.
Example (Brasero): an employee on `/admin/inventario` must not see a working "Nuevo artículo"; `/admin/balance` as employee must redirect to `/admin` per `requirePermiso`.

**Destructive actions, confirmation and undo**
List from source every handler that deletes data, cancels a paid or confirmed order or booking, refunds, voids, closes a period, or moves money; then trigger each in your own tenant on fixture data you created for it. For each one, record which guard exists, then check the rules:
- At least one of three guards applies to every submission that creates a financial or legal commitment or changes or deletes user data: the action can be reversed, the input is checked with a chance to correct it, or the user reviews and confirms before it is final. None of the three is a finding whose impact follows what is lost [rule: WCAG-28, UX-21].
- Each destructive or money action is guarded by undo or by a confirmation; one that runs on a single click with neither is a finding [rule: UX-27]. The reverse also holds: a confirmation on a frequent, cheap, reversible action trains users to click through it, and is reported as `low` [rule: UX-27].
- A confirmation names the affected item as the screen names it, says what will happen, labels its buttons with verbs that describe the outcome (not OK, Yes or No alone), and does not put initial focus on the destructive button. Read the dialog's text, button names and `document.activeElement` in an `evaluate` assertion when the `role=dialog` or `role=alertdialog` element appears. "Are you sure?" as the whole message is a finding. Typing a word to confirm is allowed for rare, very costly actions [rule: UX-28].
- A destructive control does not sit next to a frequent benign control with the same styling; there is at least one extra cue (label, icon, position or spacing), and the two targets meet the 24 px target-spacing minimum [rule: UX-29, WCAG-24].
- When undo is offered in a toast or snackbar, it is reachable by keyboard, does not disappear while focused or hovered, and stays at least about 10 s; measure its lifetime with a `waitFor` on its appearance and an `evaluate` assertion that it is still present at the deadline. An error is never shown only in a self-dismissing toast [rule: UX-30].
- Every dialog that asks for confirmation can be left without acting: a Cancel or Close control and the Escape key for dialogs that are not critical [rule: UX-31].
- Leaving a form with unsaved changes (an in-app link, browser Back, closing the dialog, closing the tab) either keeps a draft or warns first; the browser-level warning is registered only while there are unsaved changes, because an always-on `beforeunload` handler also hurts back/forward restore. In-app route changes need the router's own guard; `beforeunload` does not cover them [rule: UX-32].
After the action, check the outcome where it lands: the record gone or in its cancelled state, stock and money movements reversed as the rule says (`count_command` before and after), and undo restoring exactly what was there.
Example (Brasero): cancelling an order on `/admin/pedidos` must name the order (table or customer and total) in its confirmation and return the stock; "Cerrar turno" on `/admin/caja` commits money and must show the totals being closed before it commits.

## Universal moves (they cut across every class above)

- Before any runtime step, write the expected outcome as a check `expectation` with its source, then run, then fill `result`. A check whose expectation was written after the observation is not evidence.
- Follow one scenario across every screen it touches in a single tenant, and keep a figure ledger (route, label, parsed value, raw text, capture file) in `scratch/out/`; most defects in this file appear as a disagreement between two lines of that ledger.
- Locate controls by role and accessible name first and by CSS last; a control you can reach only through a structural selector is a lead for the accessibility lens [rule: E2E-05]. After a step that changes route, wait for the destination URL or a landmark unique to it, not for a generic navigation event [rule: E2E-06].
- When a result changes between runs, do not average it away and do not drop it. Rerun the unit alone in a fresh context three times as [HUNTING.md](HUNTING.md) describes; two failures out of three is reproducible; otherwise record the class (product race, probe wait, order dependency, data dependency, environment, external, time, unknown) in the check result. Races are this file's main subject, so a product race found here is a candidate even when intermittent [rule: E2E-14, E2E-15, E2E-16].
- When a root cause is `high` or `blocker`, look for the same cause on the other surfaces you own (another dialog using the same action, another screen using the same total) and add them to `also_affects`; do not reach into units owned by other hunters.
- Ask a consult when the decisive question belongs to another lens: whether an error is announced (ACCESSIBILITY.md), whether a delay is a performance root cause (PERFORMANCE.md), whether a state is designed at all (RESILIENCE-AND-STATES.md). Put the question, your position and your evidence in `consults`; do not settle it by guessing.

## Validation rules (checked before any finding from this file is reported)

1. State the rule and its source exactly: the code path with anchor, the product document heading, the confirmed `PR-` row, the `RULE:` id from [SOURCES.md](SOURCES.md), or the canonical sibling screen (and why it is canonical). A figure without its rule is an observation, not a finding.
2. Show the outcome where it lands: the second screen, the list, the export, or the `count_command` output before and after. For double submit, races and destructive actions, the count is the evidence; the button's look is not.
3. Put the measured value next to the threshold: the parsed figures on both screens, the message texts for each cause, the toast lifetime, the field count. A heuristic-based candidate without a measured value stays `needs_validation`, and a wording-judgement rule needs a second independent agent or a judge before it leaves that state [rule: UX-11, UX-41, UX-42].
4. Rule out fixture artifacts: data you created inconsistently, a tenant another agent touched, a shift opened by someone else, a throttle tripped by a peer. If the deviation disappears on fresh fixture data, it is `rejected` as a fixture artifact. An intermittent result that is not a product race goes to the report's probe-reliability section with its class, not to findings [rule: E2E-16].
5. Rule out formatter noise: a difference that disappears after parsing both sides as numbers, or after normalising U+00A0 and U+202F, is not a finding.
6. Do not extend reach or impact beyond what you reproduced. One wrong total on one data state is `segment` until you show it on `typical` data. Advisory figures (benchmark field counts, abandonment rates, platform guidance) never raise severity.
7. Use `confirmed` only with a local reproduction in the stated context, a promoted artifact, and an observed result that contradicts the stated rule. Use `needs_validation` when the decisive fact is the real server clock crossing a boundary, production-scale data, a real device or engine, a third party, or reasoning your tier could not settle, and name that fact exactly in `blockers`.
