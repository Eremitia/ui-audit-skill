# Performance Audit

#### When to use this file

Select this file when recon shows any of the following: a public or primary entry route that people open on phones (a landing, sign-in or menu page reached from a link or a QR code); screens meant to stay open for hours with polling or live refresh; client islands or client components that may pull in heavy libraries; images, fonts or carousels above the fold; lists or tables that grow with the data; a server render that awaits several data sources; or history navigation (back and forward) on a primary path. A framework name alone is not a trigger.

Neighbouring companions: [RESILIENCE-AND-STATES.md](RESILIENCE-AND-STATES.md) owns what the user sees while things are slow or failing (skeletons, pending feedback, offline); this file owns how long it takes and what it costs. [RESPONSIVE-AND-LAYOUT.md](RESPONSIVE-AND-LAYOUT.md) owns layout shift caused by breakpoints only when it is a layout defect, not a metric. [FUNCTIONAL-FLOWS.md](FUNCTIONAL-FLOWS.md) owns whether polling shows the right data; this file owns its cost. [VISUAL-AND-THEMING.md](VISUAL-AND-THEMING.md) owns pixel changes between runs; a shift or a late font found there comes here only when it is measured as a metric. Every number in this file is graded against the [Threshold table](#threshold-table) below; the rule ids cited in square brackets resolve in [SOURCES.md](SOURCES.md).

## Core discipline (goes into every prompt that uses this file)

```
- Measure only a production build started inside the proven sandbox topology. A development server, a warm cache or an unrecorded topology produces no performance evidence at all.
- Every number is compared with a stated threshold from this file's threshold table or the repository, recorded as a measurement with value, unit, threshold, pass_if, runs, aggregation and profile. A metric with no threshold and no user consequence is not a finding.
- Use the lab protocol of the run profile: one discarded warm-up, then 3 cold runs (quick) or 5 cold runs (standard, deep) with the cache disabled; report the median, and the worst run for CLS and INP. Mobile is m390 with slow4g and CPU 4x; desktop is d1440 unthrottled.
- Numbers are lab numbers. Never write that a page "passes" or "fails" Core Web Vitals; write that the lab median meets or misses the good threshold under a named profile.
- A VM forwarding hop inflates TTFB and LCP. Record the topology and the host facts with every measurement and do not attribute VM or host overhead to the application.
- Name the cause, not only the symptom: the LCP element, the shifting node, the oversized chunk, the request chain, the long frame's script or the bfcache blocker. A finding without a cause is an improvement note.
- Measure alone. Every unit whose lens is a class of this file runs in the dedicated performance wave, one runtime agent at a time; its verifiers also run alone. A number taken while another agent drives a browser, the same app server or the same VM is contaminated and is not evidence.
- Probe evaluate steps are assertions: the probe records the expression and whether it threw, never a returned value. To read a number, throw an Error whose message carries only that number and the threshold.
- Report your self-assessment honestly; ask a consult instead of guessing outside this lens.
```

Scheduling the performance wave (parent): this follows the dedicated-waves rule of [HUNTING.md](HUNTING.md) (grouping rule 6). Hunters in an ordinary wave run in parallel, and each launches its own browser against the same app server and the same host. That load alone moves LCP, INP, TBT and TTFB, which yields false failures, or false passes once a verifier measures in a quiet moment. A single lab run is not a result and measurements must never run side by side on one machine [rule: VITALS-16]. So the parent:

- puts every unit whose `lens` starts with `PERFORMANCE.md#` into the performance wave, after the ordinary waves and the server-zone wave and before the throttle and login wave; its hunters run one at a time, each alone, with no other hunter, verifier, consult peer, judge, sweep or fixture agent driving a browser or touching the app; escalated performance units take sequential slots appended to the end of that wave;
- runs every verifier of a performance fingerprint (Phase 3, Phase 5, a replacement verifier, a fallback panel member) alone as well, with nothing else active;
- records in `run-metadata.json`, right before that wave, `sandbox.host_facts.free_memory_at_perf_wave` and `sandbox.host_facts.cpu_benchmark_ms` (the median of the probe's `summary.hostBenchmark`), next to the `cpu`, `total_memory` and `vm_limits` facts recorded at setup, so every measurement is read against the machine that took it [rule: VITALS-15];
- ignores `sandbox.max_parallel_browsers` inside this wave (it caps browser-driving agents in every other wave only).

A performance record whose capture overlapped another runtime agent is re-measured in the dedicated wave, or stays out of findings.json.

## Threshold table

One table grades every figure, in the probe, in hunter results and in the report [rule: VITALS-30]. "Good" is inclusive (a value equal to the good threshold passes); "poor" means strictly above the poor threshold; the band between is "needs improvement". In a record, `threshold` is the good value and `pass_if` is `<=`.

| Metric | Record metric | Probe field | Good (≤) | Poor (>) | Aggregation | Rules |
|---|---|---|---|---|---|---|
| Largest Contentful Paint | `lcp_ms` | `vitals.lcpMs`, `vitals.lcpElement` | 2500 ms | 4000 ms | median | [rule: VITALS-02, TOOLS-21] |
| Interaction to Next Paint | `inp_ms` | `vitals.inpMs` | 200 ms | 500 ms | max (worst run) | [rule: VITALS-03, TOOLS-21, TOOLS-22] |
| Cumulative Layout Shift | `cls` | `vitals.cls`, `vitals.clsSources` | 0.1 | 0.25 | max (worst run) | [rule: VITALS-05, TOOLS-21, TOOLS-23] |
| First Contentful Paint | `fcp_ms` | `vitals.fcpMs` | 1800 ms | 3000 ms | median | [rule: VITALS-09] |
| Time to First Byte | `ttfb_ms` | `vitals.ttfbMs` | 800 ms | 1800 ms | median | [rule: VITALS-08] |
| Total Blocking Time, mobile viewport | `tbt_ms` | `vitals.tbtMs` | 200 ms | 600 ms | median | [rule: VITALS-11, TOOLS-17] |
| Total Blocking Time, desktop viewport | `tbt_ms` | `vitals.tbtMs` | 150 ms | 350 ms | median | [rule: VITALS-11, TOOLS-17] |
| Long task or long animation frame | `long_task_ms` | `vitals.longTasks.maxMs` | 50 ms | none | max | [rule: VITALS-10] |

Additional lab signals, never a finding on their own: Lighthouse's stricter desktop lab bands, LCP good up to 1200 ms and poor above 2400 ms, FCP good up to 900 ms and poor above 1600 ms, apply to d1440 captures as a supporting note next to the primary row above [rule: VITALS-13]. Speed Index is not measured by the probe. TBT is a lab proxy for responsiveness: a page can show good TBT and poor INP, so TBT never clears an INP failure [rule: VITALS-11].

Skill defaults (engineering choices of this skill, labelled as such in reports, overridable by a repository budget): initial script per route about 170 KB compressed, flag above 250 KB, any single chunk above 100 KB; an image oversized when its natural width exceeds rendered width × DPR × 1.5; rendered versus natural aspect ratio within 2 %; RSC or route payload above 50 KB; more than 1,500 DOM nodes on a page; a list above 50 items with no virtualisation or `content-visibility` as a lead, and above 1,000 rendered rows flagged outright [rule: FRAMEWORKS-65]; more than 50 nodes mutated per keystroke; visible feedback within 300 ms and a pending indicator within about 100 ms; the ten largest client modules listed per route [rule: FRAMEWORKS-22]; CPU slowdown 4x [rule: FRAMEWORKS-11]. A repository budget (a size-limit config, `chunkSizeWarningLimit`, Angular budgets) replaces the matching default and is cited as the expectation.

Severity follows [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md); the band is stated with the number, and a `high` that rests on a poor-band value stands only when the verifier's own median (worst run for CLS and INP) also lands in the poor band.

## Lab protocol

- **Runs by profile.** Probe config `warmup: true` plus `repeat: 3` in quick, `repeat: 5` in standard and deep (the probe's maximum), `checks.vitals: true`, `checks.resources: true`. Five runs give a markedly steadier median than one [rule: VITALS-16, VITALS-01]. The probe disables the cache for every run, so each `.r<k>` capture is cold. Take the median yourself from the `.r<k>` captures; for CLS and INP use the worst run. In quick, 3 runs is a skill reduction below VITALS-16's minimum of 5; a high severity resting on a quick-profile median needs a 5-run verifier [rule: VITALS-16].
- **Profiles.** Mobile: viewport m390, `network: "slow4g"`, `cpuThrottle: 4`. Desktop: viewport d1440, `network: "fast"`, `cpuThrottle: 1`. The probe's `slow4g` preset (150 ms latency, 204,800 B/s down, 96,000 B/s up) is close to Lighthouse's default mobile network, but it is request-level throttling applied by CDP, not Lighthouse's simulation, and is labelled as applied throttling [rule: TOOLS-16, VITALS-14]. Lighthouse emulates a 412 × 823 screen at DPR 1.75; the skill's m390 numbers are comparable to a Lighthouse report only loosely. Run both viewports for loading classes, because the LCP element can differ between them [rule: VITALS-18].
- **Host calibration.** CPU throttling is a multiplier on the host's own speed. With `benchmark` on (the probe's default when `checks.vitals` is set and `repeat > 1`), the probe records `summary.hostBenchmark` (three timed runs, `medianMs`, `cpuThrottle`); the parent copies the median into `sandbox.host_facts.cpu_benchmark_ms`. When a verifier's benchmark median falls outside the range of the hunter's three benchmark runs, the host changed between the two measurements: compare only after re-measuring both under the same conditions [rule: VITALS-15].
- **Production build only.** The command that built and started the target is recorded in run metadata (for example `next build` then `next start`, `vite build` then `vite preview`, `nuxt build` then `nuxt preview`, `astro build` then `astro preview`, `ng build` with the project's server). A capture from a development server is never performance evidence; at most it is a lead marked "development build, indicative" [rule: VITALS-28, FRAMEWORKS-10].
- **What the probe measures and how.** Observers are registered with `buffered: true` by an init script that runs before page scripts [rule: VITALS-29]. LCP stops at the first scripted input and CLS uses session windows (gap under 1 s, window at most 5 s, the largest window kept, shifts within 500 ms of discrete input excluded) [rule: TOOLS-23]. The probe reads final CLS and INP values from the page before it closes or navigates away, never from unload events [rule: VITALS-22]. Where an entry type is unsupported, the field is null and is reported as "not measurable in this engine", never as zero [rule: TOOLS-24].
- **Load pass versus interaction pass.** A load capture yields LCP, FCP, TTFB, load-time CLS and TBT; an interaction capture (with steps) yields INP, CLS after load and long tasks. Never report LCP from an interaction capture [rule: VITALS-17].
- **Only stable metrics gate.** LCP, INP and CLS are the Core Web Vitals; FCP, TTFB and TBT are supporting metrics. First Input Delay is retired and never used as a gate [rule: VITALS-06, VITALS-07].

Lab is not field. Core Web Vitals are defined at the 75th percentile of real page loads, per device class [rule: VITALS-01]. Lab runs differ from field data by design: one device, one network, a cold cache, no bfcache, scripted input, a session that ends when the probe stops [rule: VITALS-18]. A private or local app has no public field data, and the skill never queries one (no traffic leaves loopback) [rule: VITALS-19]; when the project ships its own field reporting (`web-vitals`, a framework reporting hook) [rule: FRAMEWORKS-38], the report says it exists and where, and field claims stay `needs_validation`. Lighthouse is not run by this skill; when the project already keeps Lighthouse JSON reports, read the score, its weights and the five metric values only as context, never as the probe's evidence [rule: TOOLS-15, VITALS-12]. LCP and INP exist in all major engines, CLS and long animation frames only in Chromium, and engines measure slightly different end points, so numbers are compared only within one engine [rule: VITALS-20].

Soft navigations. A client-side route change is not a page load. Measure a navigation click as an interaction (INP of the click). Where the browser exposes `soft-navigation` entries (feature-detect through `PerformanceObserver.supportedEntryTypes` in an evaluate assertion), a paint figure for the new view may be read with the same thresholds; otherwise record "soft-navigation paint not measurable" [rule: VITALS-21].

## Framework notes

Apply only the row of the framework recon detected (see `tools/project-detect.json`); other rows are silent. Each row names what to check before or alongside the probe numbers; a static hit is a lead until a browser measurement shows its cost reached the user.

| Framework | Production commands | Checks |
|---|---|---|
| Next.js (App Router) | `next build`, `next start` | `'use client'` on layouts, pages or large static trees [rule: FRAMEWORKS-19]; `next build` prints no bundle sizes since v16, so per-route transfer from the probe is primary and the bundle analyzer runs in the build copy for attribution [rule: FRAMEWORKS-22]; heavy, rarely used client code statically imported instead of lazy loaded [rule: FRAMEWORKS-24]; `<Image>` without dimensions or `fill`, and responsive or `fill` images without `sizes` [rule: FRAMEWORKS-25, FRAMEWORKS-26]; the LCP image lazy or without `loading="eager"`, `fetchPriority="high"` or `preload` (the `priority` prop is deprecated from v16, so its absence is not a finding) [rule: FRAMEWORKS-27]; fonts not loaded through `next/font`, called more than once per family, or with fallback adjustment disabled [rule: FRAMEWORKS-29, FRAMEWORKS-30]; third-party scripts eager without reason [rule: FRAMEWORKS-31]; sequential independent awaits in server components, or server components fetching their own route handlers [rule: FRAMEWORKS-35]. |
| Vite with React or Vue | `vite build`, `vite preview` | chunks above `build.chunkSizeWarningLimit` (500 kB uncompressed by default), or a raised limit with no reason [rule: FRAMEWORKS-53]; pages imported statically in the router so the first load carries other routes [rule: FRAMEWORKS-54]. |
| Nuxt | `nuxt build`, `nuxt preview` | Vue list cost: unstable props per item, unvirtualised lists of thousands of rows, deep reactivity on large immutable data [rule: FRAMEWORKS-65]. |
| SvelteKit | `vite build`, `vite preview` | load functions chaining requests that could run together, the same check as the server waterfall class [rule: FRAMEWORKS-69]; preview build only. |
| Astro | `astro build`, `astro preview` | islands hydrated with `client:load` while outside the first viewport, where `client:idle`, `client:visible` or `client:media` would do [rule: FRAMEWORKS-73]. |
| Angular | `ng build`, then the project's static or SSR server | `angular.json` production budgets present and met (defaults: initial warning 500 kB, error 1 MB; component style warning 2 kB, error 4 kB) [rule: FRAMEWORKS-78]. |
| React Router (framework mode) or Remix | the project's build and `start` scripts | when the config renders only the root route on the server (SPA mode), first-paint findings are judged as a client-rendered app [rule: FRAMEWORKS-84]. |
| Plain static site | `scripts/static-serve.mjs` on loopback | images, fonts and render-blocking resources only. |

Example (Brasero): Next.js 16 App Router; `next build` and `next start` run in the build copy, `next experimental-analyze` gives attribution, and the repository rule asks for server components by default with `"use client"` only on the interactive leaf.

## Loading classes (subagent_type: `general`)

**Largest paint and render-blocking**
Check how long the primary content takes to appear and what delays it. Thresholds: the LCP, FCP and TTFB rows of the threshold table [rule: VITALS-02, VITALS-09, VITALS-08]. Reproduce with the lab protocol in both profiles and read `vitals.lcpMs`, `vitals.lcpElement`, `vitals.fcpMs` and `vitals.ttfbMs` from every `.r<k>` capture. On a route with steps, input ends LCP recording and a step may navigate, so the probe also keeps the load metrics read before the first step (`vitals.beforeSteps`); `vitals.lcpSource` says whether `lcpMs` is the end-of-capture value or the before-steps one. Then explain the gap: is the LCP element an image marked `loading="lazy"` (a defect on its own when it is the LCP), an image without a priority hint, text waiting on a font, or content that only renders after a client fetch [rule: FRAMEWORKS-27]? Chromium does not count fully transparent elements, elements that cover the whole viewport, or low-detail placeholder images as LCP candidates, so a surprising LCP element is often the real content behind such a placeholder. On loopback the network is near zero, so a high TTFB points at server work (rendering, data fetching); a TTFB that appears only across a VM forwarding hop is `needs_validation` with the hop as its blocker. Render-blocking resources are scripts or stylesheets that finish before FCP in the resource timing; cite them by URL. A missing `width=device-width` viewport meta is its own finding on mobile, because it adds tap delay to every interaction and changes the LCP element [rule: VITALS-18]. Field p75 values on real phones are not locally reproducible; claims about them are `needs_validation`. Example (Brasero): the cover photo or logo on `/mesa/[slug]` is the likely LCP element for a customer who scans the QR; check that it is eager, sized and served through `/_next/image` or `/imagenes/[key]` in a modern format.

**Layout shift**
Check that content does not jump while loading or after an interaction the user did not cause. Threshold: the CLS row, worst of the runs, not the median [rule: VITALS-05]. The probe computes `vitals.cls` with session windows and lists `vitals.clsSources` [rule: TOOLS-23]. Name the shifting nodes and the cause: an image or iframe without dimensions or reserved space [rule: FRAMEWORKS-25], a font swap without a matched fallback [rule: FRAMEWORKS-30], a banner or install prompt inserted above content, a skeleton whose size differs from the loaded content, deferred or lazily hydrated regions that render taller than their placeholder, or polling that re-renders a list with different heights. Field CLS covers the page's whole life, including scrolling, so after the load capture scroll the page with a `scroll` step and keep observing [rule: VITALS-05]. Shifts caused by live refresh are measured over a waiting period that covers at least two poll intervals (a `wait` step), with `freezeAnimations: false` so the capture reflects what users see. CLS is measurable only in Chromium [rule: VITALS-20]. Example (Brasero): the `InstallApp` prompt and the promo modal on the menu, and the orders board when `useLiveOrders` refreshes every 5 s.

**JavaScript weight and client boundaries**
Check how much script each route sends on a cold load. Budget: the script defaults of the threshold table, or the repository's own budget. Read `resources.scriptTransferBytes`, `resources.scriptDecodedBytes` and `resources.largestScript` from cold captures (median over the profile's runs). Per-route transfer measured by the probe is the primary number. For attribution, run the framework's analyzer in the build copy inside the sandbox, never in the owner's tree, and list the ten largest client modules with their import chains [rule: FRAMEWORKS-22]. Then trace the cause in source: a client boundary placed high in the tree so that a whole view becomes client code [rule: FRAMEWORKS-19]; a client module importing a server-weight library directly or transitively; heavy code needed only after an interaction (dialogs, editors, charts) loaded statically instead of on demand [rule: FRAMEWORKS-24, FRAMEWORKS-54]; a chunk over the bundler's or the project's budget [rule: FRAMEWORKS-53, FRAMEWORKS-78]; an island hydrated eagerly although it starts off screen [rule: FRAMEWORKS-73]. Long tasks attributed to third-party script origins during load point at script loading strategy [rule: FRAMEWORKS-31]. A source scan alone is not a finding here: a performance record needs a browser measurement that shows the weight reached the client. When the scan finds a server library in a client graph but the transfer stays under budget, record an improvement note. Example (Brasero): `exceljs`, `qrcode`, `@prisma/*` and `server-only` modules must never appear in a client chunk.

**Images and media**
Check that images are sized, compressed and loaded at the right moment. An image is oversized when `naturalWidth > renderedWidth × DPR × 1.5` (skill default) [rule: FRAMEWORKS-26]. Responsive or fill images need `sizes`, otherwise the browser assumes the full viewport width [rule: FRAMEWORKS-26]. Below-the-fold images are lazy; the LCP image is not [rule: FRAMEWORKS-27]. Every image has reserved space (dimensions or an aspect-ratio box) and keeps its natural ratio within 2 % [rule: FRAMEWORKS-25]. Served raster images are WebP or AVIF (check the `content-type` of image responses); a raw `<img>` for a raster photo, where the framework offers an image component, is a finding unless it is an SVG icon or a data URI. Measure with `resources.imageTransferBytes` and an evaluate assertion that compares `naturalWidth`, `getBoundingClientRect().width × devicePixelRatio` and the `loading` attribute of each `img` and throws with the offending counts. Record the image transfer per route as `image_transfer_bytes`. Example (Brasero): product photos in the menu grid at m390 and the large promo photo, which the owner wants large on purpose (a documented decision; judge its bytes, not its size on screen).

**Fonts**
Check that fonts load without blocking text or shifting layout. Expected: fonts come through the framework's font loader or self-hosted files with subsets and `font-display: swap` or `optional`, no browser request to a third-party font host, few families and weights, and the fallback metric adjustment left on [rule: FRAMEWORKS-29, FRAMEWORKS-30]. Measure `resources.fontCount` and look for font-load moments among `vitals.clsSources`; text reflow after a font swap should contribute no shift. A font request that appears in `blockedRequests` means the page depends on an external host: that is a finding with the dependency as its cause. A build-time font fetch is a build blocker (`build_fetch_required`), not a runtime finding. Example (Brasero): Rubik through `next/font`; count the weights actually shipped.

**Server and data waterfalls**
Check that the server and the client do not wait in sequence for data they could fetch together. Server side: two or more independent `await`s in a row in a page, layout, loader or server component, so TTFB grows with each one; a server component calling the app's own HTTP route instead of the data function [rule: FRAMEWORKS-35]; a layout that reads request data and so holds back its loading fallback. Confirm by comparing TTFB on the route with the number of sequential awaits in source. Client side: a fetch that starts only after hydration (its `startTime` later than the main script's `responseEnd`) for data the server could have rendered, data fetched on the server and fetched again by the client, or a chain of three or more dependent requests. Assert on resource timing through an evaluate step that throws with the chain's URLs and start times. Route payloads above about 50 KB (skill default; for React Server Components, requests carrying `_rsc=`, recorded as `rsc_payload_bytes`) usually mean whole database rows passed to client components. A slow TTFB alone, seen only across the forwarding hop, is `needs_validation` with the hop as its blocker; it can be `confirmed` only when it also appears without the hop (`browser-in-vm` or `host-only` topology).

## Runtime classes (subagent_type: `general`)

**Interaction latency and long tasks**
Check that the page responds quickly to real input. Thresholds: the INP row [rule: VITALS-03]; long tasks and long animation frames above 50 ms [rule: VITALS-10]; visible feedback within 300 ms for any action that takes longer, and a pending indicator within about 100 ms (skill defaults). INP needs input: a load with no interaction has no INP [rule: TOOLS-22]. Drive real interactions with probe steps (`click`, `fill`, `press`, `select`), which the CDP driver dispatches as trusted input; a script calling `element.click()` is not user input. Then read `vitals.inpMs`, `vitals.longTasks` and `vitals.tbtMs`. The probe keeps the longest event duration per interaction and reports the worst interaction; with fewer than 50 interactions that equals INP's definition. `inpMs` is null both when no step produced an interaction and when every interaction stayed under the 16 ms reporting threshold of Event Timing; `vitals.inpStatus` tells them apart (`no_interaction`, `below_threshold`, `measured`) and `vitals.interactionCount` gives the count. `no_interaction` is not a pass: the check did not run. `below_threshold` is a measured pass. Name the dominant phase of a slow interaction: input delay (`processingStart − startTime`), processing (`processingEnd − processingStart`) or presentation delay (the rest of `duration`); there is no per-phase threshold, only the 200 ms total [rule: VITALS-04]. For attribution, an evaluate assertion reads buffered `long-animation-frame` entries overlapping the interaction and throws with the script URL, function name and duration of the worst one [rule: VITALS-10]. Typing is an urgent update: a text input whose state change waits behind an expensive render, or a filter that re-renders a large tree on every keystroke, is the usual cause. Use the mobile profile; INP on d1440 without throttling rarely says anything. Example (Brasero): adding to the cart, opening `CheckoutDialog`, typing in `TabFinder`, changing an order's state on the board.

**Re-render and DOM churn**
Check that the page does not rewrite DOM when nothing changed. Install a `MutationObserver` on `document.body` with an evaluate step that only counts into a page variable, wait 10 s idle with a `wait` step, then assert on the count with a second evaluate that throws with the number. Any mutations while no data changed are suspect; name the component. In search inputs, more than about 50 nodes mutated per keystroke (skill default) is a finding when INP or long tasks show the cost. For polling screens, an identical server payload should cause zero mutations; compare two refreshes with no fixture change in between. Record `dom_mutations`. A ticking clock or a relative time ("5 minutes ago") that updates is intended churn; judge only whether it re-renders more than its own text.

**Polling and background work**
Check what a screen costs while it sits open. Measure requests per minute and bytes per poll from resource timing over at least three intervals (`requests_per_minute`). Expected behaviour: the interval suits the screen (operational screens poll no faster than every 3 to 5 s); polling pauses when the tab is hidden and resumes once on return without a burst; a new poll does not start while the previous one is pending under `slow3g`; polling backs off on error; it stops after navigation away or logout. Test the hidden tab by dispatching a `visibilitychange` with a redefined `visibilityState` in an evaluate step that changes no app data, then count requests during the hidden period. The battery and data cost on a real phone is `needs_validation`; the request count is not. Example (Brasero): `usePolling` (5 to 10 s), `useLiveTab` (8 s), `useArrivals` (5 s) and `usePanelNotices` (10 s) can all run on one panel page at once; count them together.

**Large lists and DOM size**
Check pages whose content grows with data. Flag a page above 1,500 DOM nodes (probe `domNodes`, skill default), a list above 50 items that is neither virtualised nor uses `content-visibility` as a lead, and any list rendering more than 1,000 rows [rule: FRAMEWORKS-65]. Use the `heavy` fixture state; a list that is short only because the fixture is small proves nothing. Measure the cost, not just the count: INP of scrolling or filtering that list, long tasks during first render. Lists that a project rule says must scroll inside a bounded container are a layout matter for [RESPONSIVE-AND-LAYOUT.md](RESPONSIVE-AND-LAYOUT.md); here judge only their render cost. Example (Brasero): `/admin/auditoria` with 5,000 entries and `/admin/inventario/movimientos`.

**Long-session stability**
Check screens meant to stay open all day, and flows repeated many times (open and close a dialog, go to a screen and back). Enable `checks.heap`, run at least ten cycles with `wait` or step pairs, and read `heap.samples` (JS heap used and DOM nodes after each step) and `heap.trend`. No published numeric leak threshold exists; a finding needs monotonic growth across those cycles with no data growth to explain it, and DOM nodes or listeners growing by about the same amount every cycle are stronger evidence than heap bytes [rule: VITALS-25]. The probe samples without forcing garbage collection, so a single rising heap curve is a lead, not a verdict. Name what accumulates: listeners added per refresh, intervals never cleared, arrays of notices that only grow, detached DOM trees still referenced. Isolating retained objects with heap snapshots (baseline, after the action, after undoing it) is a deep-profile task with a strong model, not a default [rule: VITALS-26]. The in-page memory measurement API needs a cross-origin-isolated document and is not comparable across versions; do not rely on it [rule: VITALS-27]. Memory pressure on a real low-end phone over a whole day is `needs_validation` with a device plan. Example (Brasero): the orders board and `/admin/caja` stay open for a whole shift on the counter device.

**Back/forward cache**
Check that going back or forward to a page restores it from the back/forward cache instead of reloading it [rule: VITALS-23]. Reproduce with probe steps: load route A, navigate to route B on the same loopback origin (a `click` on a real link, or `goto`), then a `back` step (and a `forward` step for the reverse). Each history step records `navigated`, `persisted` (the `pageshow` flag) and `notRestoredReasons` (reason strings from the navigation timing entry). `persisted: true` passes. `persisted: false` with reasons is a lead to explain; `notRestoredReasons: null` means no reasons were reported, not that the page was restored. Repeat over the profile's runs and record a measurement with metric `other`, unit `restored (1) or not (0)`, threshold 1, `pass_if` `=`, aggregation `max`. Then name the blocker in source: an `unload` listener in first-party code (use `pagehide`); `Cache-Control: no-store` on an HTML response; an open IndexedDB connection, WebSocket or in-flight request left open at `pagehide`; a window opened without `noopener` still holding a reference [rule: VITALS-24]. Reason strings change between browser versions, so match them loosely. `no-store` on an authenticated or sensitive page is often a deliberate security choice: never recommend removing it there without the project's security review; record the trade-off as an improvement, not a finding. A page that is not restored only because its content must be fresh (a till, a live board) and that says so in a documented decision is not a defect. Example (Brasero): going back from a product sheet to the public menu on `/mesa/[slug]` should restore the scrolled menu; panel pages behind the session may deliberately send `no-store`.

## Universal moves (they cut across every class above)

- Put the measurement in the record exactly as taken: metric from the enum, value, unit, threshold and `pass_if` from the threshold table, `runs` (the profile's run count), `aggregation` (`median`, or `max` for the CLS and INP worst run) and a `profile` string that names viewport, network, CPU throttle and topology, for example `m390 slow4g cpu4 nat-forward`. Cite the rule in the expectation as `RULE:<id>` (for example `RULE:VITALS-02`) or the repository budget that replaced it.
- Report the band next to every number (good, needs improvement, poor) and label it lab.
- Compare the failing route with a sibling route in the same build and profile. If the sibling is just as slow, suspect the environment or a shared cause in a `shared_ui_files` entry before blaming the route.
- For every confirmed cause, state the smallest source change and a regression check that a maintainer can rerun: the probe config with the same profile, or a size assertion on the analysed chunk.

## Validation rules (checked before any finding from this file is reported)

1. The record uses `execution.method: browser`, `build_mode: production`, a real `topology`, and at least one measurement with `runs >= 3` (5 in standard and deep). The validator rejects anything else for a lens in this file [rule: VITALS-28, FRAMEWORKS-10].
2. Each measurement's value must fail its own passing condition (`value <pass_if> threshold` is false). A route that meets the threshold is not a finding, however close it is.
3. A verifier, running alone with no other runtime agent active, reproduces the number with its own warm-up and the profile's cold runs. If the verifier's median passes, the record is rejected or demoted; a single bad run is noise, except for the worst-run rule on CLS and INP, which the verifier must also observe [rule: VITALS-16].
4. Rule out environment artifacts before blaming the app: the VM hop, a capture taken while other agents loaded the host or the app, a host benchmark that moved between hunter and verifier, a development build, a warm cache, a fixture that is unusually large or small, and blocked external requests that would have succeeded in production. A metric that depends on any of these is not `confirmed` [rule: VITALS-15].
5. Never state or imply a Core Web Vitals assessment: no "passes", "fails" or "meets Core Web Vitals" in any record or report text; lab numbers are labelled lab and graded by band [rule: VITALS-01, TOOLS-21].
6. Use `confirmed` only when the metric fails its threshold in the verifier's own runs and the cause is named in source or in the captured timeline. Use `needs_validation` when the decisive fact is a real device, a real network, production data volume, field p75 values, another engine, or a TTFB difference that may come only from the forwarding hop.
