# Resilience and States Audit

#### When to use this file

Select this file when recon (1b and 1d in [RECONNAISSANCE.md](RECONNAISSANCE.md)) found at least one of these:

- screens that fetch data on the server or client, so they have a loading moment;
- lists or dashboards that can be empty;
- actions that send data to the server (forms, server actions, API calls);
- an authenticated area with a session that can end;
- screens that refresh themselves, run timers, or stay open for hours;
- sounds, browser notifications, toasts or install prompts;
- route segments that can fail, be missing, or be forbidden.

Almost every web application qualifies; record in architecture.md which of these surfaces exist, because classes without a surface are excluded with a reason.

Neighbouring files: [FUNCTIONAL-FLOWS.md](FUNCTIONAL-FLOWS.md) owns whether a working flow gives the right result, including duplicate records and destructive-action guards; this file owns what the user sees when the flow is slow, fails or is interrupted. [PERFORMANCE.md](PERFORMANCE.md) owns how fast things are, what polling costs and whether a page is eligible for the back/forward cache; this file owns what the user is told while waiting and whether a restored page tells the truth. [ACCESSIBILITY.md](ACCESSIBILITY.md) owns whether status and error messages are announced. [PROJECT-CONVENTIONS.md](PROJECT-CONVENTIONS.md) supplies `PR-` rows such as "every screen defines loading, empty and error".

#### Framework conventions for states

Read the detected framework from `tools/project-detect.json` (the `framework` of the audited app) and use the matching row; a framework not in the table, or a cell marked "read the source", has no convention this skill relies on, so the expectation comes from the app's own code or a `PR-` row. A missing convention file is a lead, not a finding: the finding is what the user then sees.

| Detected framework | Loading | Errors | Not found | Hydration signal |
|---|---|---|---|---|
| `nextjs` (App Router) | `loading.(js\|tsx)` in the segment or an explicit `<Suspense>` around the awaited part [rule: FRAMEWORKS-12]; a layout that awaits runtime data outside its own boundary blocks its segment's loading view [rule: FRAMEWORKS-13] | `error.(js\|tsx)` as a client component with a retry control [rule: FRAMEWORKS-14]; `global-error.(js\|tsx)` with its own `<html>`, `<body>` and theme [rule: FRAMEWORKS-15]; production replaces server error text with a digest, so the UI must not print `error.message` as if it meant something [rule: FRAMEWORKS-16] | `not-found.(js\|tsx)`; status 404, or 200 plus a `noindex` robots meta when the decision came after streaming started [rule: FRAMEWORKS-17]; `global-not-found` when there is no single root layout [rule: FRAMEWORKS-18] | React hydration errors (see `Hydration mismatches`) [rule: FRAMEWORKS-39] |

For every detected framework, the error-state units exercise at least its not-found path and, where a safe trigger exists, its error boundary, in both themes [rule: FRAMEWORKS-85].

#### Feedback timing

Waiting feedback is judged against measured bands, not taste [rule: UX-01]:

| Time from the user's action | Expected | Decided by |
|---|---|---|
| up to 100 ms | no indicator needed; this skill's target for a pending sign on a slow action is that it appears by then (skill threshold) | [rule: UX-01, FRAMEWORKS-50] |
| over 1 s | something visible has changed (an indicator, the control's busy state, the result); nothing visible after 1 s while the action still runs is a finding | [rule: UX-01] |
| about 2 to 10 s | a looping indicator, or a skeleton for a page or section load | [rule: UX-03] |
| 10 s or more | percent done, a count ("3 of 50") or the item being processed, and a working cancel control | [rule: UX-03, UX-04] |

Measure instead of eyeballing. The probe records whether an `evaluate` step threw and its error text, never a returned value, so a timing check is three steps: (1) an `evaluate` that installs instrumentation only, adding a capture-phase `click` listener that stores `performance.now()` and a `MutationObserver` on the affected region that stores the first time an indicator, the control's disabled or busy state, or the result appears (and when an indicator disappears), all in one `window.__uiAudit` property, without touching app state; (2) the `click`; (3) an `evaluate` assertion, written as an async function called at once, that waits a stated interval (a measured interval, not a readiness wait [rule: E2E-01]), computes `feedback_ms`, and throws a message such as `feedback_ms=1840 > 1000` when the band is missed. The thrown text is the measurement for the record's `feedback_ms`. Run it under the throttled profile you name in the check (`slow3g` adds 2,000 ms of latency), because loopback answers faster than any real network [rule: UX-01].

Two failures in the other direction:
- An indicator that appears and disappears within 300 ms on the unthrottled run and moves the layout is a flash (`low`; skill threshold); an inline busy state on the control that moves nothing is not [rule: UX-02].
- A skeleton shown while a mutation (POST, PUT, DELETE) is in flight is the wrong kind of indicator (`low`); skeletons are for loading content, progress bars for uploads, downloads and conversions [rule: UX-05].
Before judging a React fallback as stuck, wait at least 300 ms, because React reveals suspended content in batches no more often than that [rule: FRAMEWORKS-47].

## Core discipline (goes into every prompt that uses this file)

```
- Every state is a screen. For each surface, name the designed loading, empty, error, not-found and forbidden states (or their absence in source) before you test them. A blank area, a spinner that never ends, a raw stack trace, a framework default error page, or a success message for something that did not save is a defect.
- Break things only from the browser side and only inside your own tenant: setNetwork (offline, slow3g, the flaky network profile), clearCookies, newTab, rotate, back, forward. Never stop the database, restart the server, run seed or reset, or edit source to inject a failure.
- A failed action must keep the user's input, say what happened in words, and allow a retry. Check all three every time; check the outcome with the list or the read-only count, not with the message.
- Time is measured, not judged: name the band (100 ms, 1 s, 10 s) and the throttled profile, and record feedback_ms from an evaluate assertion.
- Capture states on purpose: screenshot steps at the moment the state is visible, viewport-only, with polling waited out. Wait on a visible condition with a deadline, never on a fixed sleep or on network idle. A full-page capture or a frame taken mid-transition does not prove a missing state.
- Use confirmed only for states you reproduced locally in the stated context with promoted evidence. Use needs_validation when the decisive fact is a real network, a real OS notification, a deployment, rebuild or server restart, a whole-server failure, a real device, or the real server clock.
- Report your self-assessment honestly; ask a consult instead of guessing outside this lens.
```

## Screen states classes (subagent_type: `general`)

**Loading states**
For each route and each client-side fetch, check what the user sees between the click and the data. Expected: something appears at once on navigation (a skeleton, a route-level loading view, or the old content kept with a pending sign), it has the shape of what is coming (no large jump when data lands; layout shift itself is measured under `PERFORMANCE.md#Layout shift` in [PERFORMANCE.md](PERFORMANCE.md)), its kind matches the expected wait (see Feedback timing) [rule: UX-03, UX-05], and it never stays forever. Reproduce with the route at `network: slow3g` and `screenshot` steps right after `goto` and again after `waitFor` the content selector. A `waitFor` that times out is itself an observation: record the step's `ok: false`. Read source in parallel with the framework row above: which segments have a route-level loading view, which await data in a layout that blocks its own children's fallback [rule: FRAMEWORKS-12, FRAMEWORKS-13], and which components fetch in an effect under a Suspense boundary and so show nothing [rule: FRAMEWORKS-49]. More than three separate fallbacks visible at once on one screen is a review item for an uncoordinated loading sequence (skill threshold) [rule: FRAMEWORKS-48]. A filter or tab change that replaces content already on screen with a fallback, when the content's identity did not change, is a finding [rule: FRAMEWORKS-47].
Example (Brasero): the `(menu)` group and `/admin/ajustes/horario` have no `loading.tsx`, so check what `/mesa/[slug]` shows on slow3g before the menu streams in; the owner's rule asks for skeletons on entry and on navigation.

**Empty states**
For every list, table, chart and dashboard card, load the `empty` data state and look for a designed empty view: a message that the result is empty, distinct from loading and from error, and, when the user can fill it, a direct action to do so [rule: UX-40]. A heading over nothing, a zero-height box, a chart with axes and no message, or a "0" that means "never loaded" is a defect when the repository or a canonical sibling defines an empty view. The worst case is a false empty: a "nothing here" message shown while the request is still pending, which teaches users to distrust the screen [rule: UX-40]. Test it without interception: on `typical` data (not empty) at `slow3g`, take `screenshot` steps right after `goto` and after `wait` `{ms: 1000}`, before any `waitFor`; an empty message in either frame is the finding. Also test `one` (singular grammar, layouts that assume two columns) and a filter that returns nothing on `typical` data, which must read differently from a truly empty list and offer clearing the filter.
Example (Brasero): the owner's preference requires the `EmptyState` invitation (brand-coloured icon, title, one sentence, primary button); check `/admin/balance` for a range with no sales and `/mesa/[slug]` with an empty catalogue.

**Error states and boundaries**
Find out from source, with the framework row above, which segments have an error boundary, a root-level error view and a not-found handler, and which errors are caught inside components [rule: FRAMEWORKS-14, FRAMEWORKS-15, FRAMEWORKS-64, FRAMEWORKS-67, FRAMEWORKS-77]. Then trigger what can be triggered without breaking shared infrastructure: a malformed or nonexistent ID in a dynamic segment, a query parameter the page does not expect, a business-rule rejection from the server, and an action submitted after `setNetwork` `offline`. Expected: a designed message in the app's shell, language and current theme; a way back or a retry that works [rule: UX-31]; and nothing that looks like a crash. On a production build, the error view never shows a stack trace, an internal message or a bare status code [rule: FRAMEWORKS-16]. A root-level error view is a separate document in some frameworks and does not inherit the app's theme; capture it in both themes [rule: FRAMEWORKS-15]. Whole-server failure (database down, process crash or restart) would affect every agent and the run's sessions, and no phase stops or restarts the app mid-run, so it is never produced at runtime. A unit about it is source-only (context `static`, `source` checks: which boundary would catch the failure and what it renders), and any claim about what the user actually sees is `needs_validation` with the missing server failure named in `blockers`.
Example (Brasero): there is no `error.tsx`, `global-error.tsx` or `not-found.tsx` anywhere in `src/app`, which conflicts with the "Estados completos" rule; record what the user actually sees at `/admin/inventario/<malformed-id>`.

**Not found and forbidden**
Open every route URL directly: logged out (no `storageState`), as each persona, with a nonexistent ID, with an ID or slug from another tenant, with a malformed ID, and with a made-up path such as `/__ui_audit_missing_<random>`. Expected: a login redirect that brings the user back to where they were going, a designed not-found or forbidden view, a redirect to a page the role can use, and never a white screen or stack trace. Read the capture's `route.status`: an unknown URL answers 404, or, where the framework allows the decision after streaming starts, 200 with a `noindex` robots meta [rule: FRAMEWORKS-17]. The other-tenant case is reported here only as the visible result (a raw error or a page that half-renders) and is referred to the project's security review; do not try to read or change the other tenant's data.
Example (Brasero): `/mesa/no-such-slug`, `/admin/balance` as employee (`requirePermiso` redirects to `/admin`), and `/admin/pedidos` with the account session but no PIN turn (`verifyTurn` redirects to `/admin/turno`).

**Hydration mismatches**
A server-rendered page whose first client render differs causes flicker, lost input, or console errors, and in the worst case handlers attached to the wrong elements, so a confirmed mismatch is at least `medium` impact; the target is zero on every audited route, theme and viewport [rule: FRAMEWORKS-39]. Match the framework's own signal from the table above in the capture's `console` and `pageErrors`: React's hydration message, and in a production build its minified errors 418, 423 and 425; Vue's mismatch warnings [rule: FRAMEWORKS-63]; Svelte's `hydration_*` warnings [rule: FRAMEWORKS-71]; Angular's NG05xx errors [rule: FRAMEWORKS-81]. Dev-only warnings need a dev-mode run, which is never performance evidence. The common causes are dates and numbers formatted with the server's zone or locale and then again with the browser's, random values, reading browser storage or `window` during render, and invalid nesting such as a block inside a paragraph or a button inside a button [rule: FRAMEWORKS-40]. Reproduce with `timezone` set far from the server zone (`tz=Asia/Tokyo`) and `locale` changed, then compare the server HTML text (first capture) with the hydrated text after `settleMs`; check nesting with an `evaluate` assertion that throws when `p p, p div, p ul, p ol, a a, button button` matches anything. A value that changes visibly after load is a defect even without a console error. A hydration-suppression escape hatch on a leaf with an unavoidable difference (a timestamp, the theme attribute on the root element) is a documented decision, not a finding; one placed on an element with element children hides structural differences and is a lead [rule: FRAMEWORKS-41].
Example (Brasero): the server renders in America/Bogota; a time on `/admin/pedidos` rendered with the browser's zone would jump on hydration for a Tokyo browser. The theme script's `suppressHydrationWarning` on `<html>` is a documented decision.

## Network classes (subagent_type: `general`)

**Offline and flaky network**
Mid-flow, apply `setNetwork` `offline`, perform the next action, take a `screenshot`, then `setNetwork` `fast` and retry. Repeat with the `flaky` network profile (offline for `offlineMs` every `cycleMs` on top of its base profile) across a flow that sends two or more requests. Expected: a visible message that the action did not go through, every non-secret field still holding what the user typed [rule: UX-13], a working retry once online, no optimistic "saved" left on screen for something that did not save, and no duplicate when the retry succeeds (check with the list or `count_command`). Results under the flaky profile depend on where the cycle falls, so rerun before reporting and classify a non-reproducing result as [HUNTING.md](HUNTING.md) describes instead of dropping it [rule: E2E-15, E2E-16].
Example (Brasero): CheckoutDialog "Enviar pedido" while offline must keep the cart and must not show the order as sent; after coming back, one retry must produce one order.

**Slow responses and pending feedback**
Under `setNetwork` `slow3g`, measure each primary action with the three-step timing check from Feedback timing, and take a `screenshot` right after the click and again after `wait` `{ms: 300}`. Expected: a pending state on the triggering control or the region it affects, visible within the bands above [rule: UX-01, UX-07]; for a framework with a pending primitive (a form status hook, navigation state), that primitive is actually wired to something visible [rule: FRAMEWORKS-50, FRAMEWORKS-83]; feedback that is announced without stealing focus (judged by the accessibility lens; record what you saw) [rule: UX-06]; no silent timeout; and no navigation that leaves the action's result unreported. Whether a second click sends a second request is counted under `FUNCTIONAL-FLOWS.md#Double submit and idempotent actions`. For anything that runs 10 s or more under the throttled profile (imports, uploads, report generation, bulk changes), look for percent done or a count, and a cancel control that really stops the work (the request aborted or the state rolled back) [rule: UX-03, UX-04]. Run the unthrottled variant too, for the flash rule [rule: UX-02]. A spinner that hides the form's content is acceptable; one that hides an error is not.
Example (Brasero): "Cerrar turno" on `/admin/caja` under slow3g must show that it is working and must not let the user leave believing the shift is closed.

**Failed mutations**
A mutation can fail because of the network, because the server refuses it (validation, a business rule, a stale entity), or because the session ended. Cover each cause you can produce locally: offline as above; a server refusal by submitting a value the server rejects; a stale entity by changing it in a second tab (`newTab`) or second persona first. Expected: the message names the cause in the user's language, form values survive [rule: UX-13], the screen does not claim success, and the list returns to the true state on the next refresh. An error shown only in a toast that dismisses itself is a finding; a toast that carries an error or an action stays at least about 10 s and does not vanish while focused or hovered, unless the same information is available elsewhere [rule: UX-30, WCAG-14, WCAG-39]. Pausing request interception is not available (it distorts timing), so a forced 500 from a healthy server is not produced; claims that depend on one are judged from source and are `needs_validation`.
Example (Brasero): EditOrderDialog saving a quantity for an order another tab just cancelled must explain the conflict, not show the edited order as saved.

## Session and lifecycle classes (subagent_type: `general`)

**Session expiry and re-entry**
Simulate expiry with the `clearCookies` step mid-flow (`session=expired`), then perform the next action. Expected: a redirect to login (or the re-entry step the app uses) that returns the user to where they were, with typed input kept or recoverable [rule: UX-13, UX-32], never a silent no-op, a raw 401, or a blank screen. Check `session=reopened` too: a fresh context loaded from the saved session state, which is what a browser restart looks like. Agents never use the login form; a unit that must test login itself runs in the final dedicated throttle and login wave on the `audit-login` tenant. If the app ends a session or a hold on a timer while the user works, the user can turn the limit off, extend it to at least ten times its length, or is warned at least 20 s ahead with a simple way to extend; real-time events and limits over 20 hours are exempt [rule: WCAG-14].
Example (Brasero): the panel PIN mark is tied to the browser session, so `reopened` must land on `/admin/turno` with a clear prompt; an expired account session during "Registrar egreso" must go to `/login` without losing the amount silently.

**Stale tabs and deploys**
Two cases. A stale tab: `newTab`, change or delete an entity in tab 1, then act on it in tab 0; expected a clear "changed or no longer exists" message and a refreshed list. A stale deploy: an open page whose server was rebuilt, so its client references actions or chunks that no longer exist; expected a hard reload or a message asking to refresh, not an unhandled error. A rebuild and restart would affect every agent, and no phase rebuilds or restarts the app mid-run, so the stale-deploy case is always source-only (context `static`, `source` checks: look for handling of missing server actions and failed chunk loads) and its runtime claim is `needs_validation`, with the plan describing a local rebuild while a page stays open, to be done outside the run.
Example (Brasero): an order list open on `/admin/pedidos` while the same order is charged from `/admin/cuentas` in another tab.

**Back, forward and refresh**
Drive history with the probe's `back` and `forward` steps (optional `tab`), and confirm where you landed with a `waitFor` on a selector unique to the expected page and the step record's `navigated` field. Checks:
- After a submit, Back must not run the action again and the browser must not ask to resend a form.
- Back is never trapped: from any page or flow step it leaves to a different URL; history manipulation that returns the user to the same URL is a finding [rule: UX-31].
- Refresh mid-flow (`goto` the current path) with a half-filled form, an open dialog, or a cart: the state is kept or the user was warned [rule: UX-32].
- Returning to a list from a detail screen keeps the filter, tab and scroll position when the URL holds them.
- When the step record shows `persisted: true` (the page came back from the back/forward cache), the restored page must not present old totals, stock or statuses as current: take a `screenshot` and compare its figures with a fresh `goto` of the same path; a restored page that silently shows stale figures is the finding here [rule: VITALS-23]. Whether the page is eligible for that cache, and the `notRestoredReasons`, belong to `PERFORMANCE.md#Back/forward cache`.
Example (Brasero): Back after "Enviar pedido" on `/mesa/[slug]` must not create a second order; refreshing `/admin/cuentas?…` must reopen the same tab.

**Hidden tab and resume**
Screens meant to stay open should pause work while hidden and catch up on return. Check from source which timers listen to `visibilitychange`, then at runtime: open the screen, `newTab` and work in tab 1 for longer than one polling interval, return to tab 0 and `screenshot`. Expected: fresh data within one interval of returning, no burst of queued alerts, and no stale "new" badges. Whether background requests really stopped needs a request-rate capture owned by `PERFORMANCE.md#Polling and background work` in [PERFORMANCE.md](PERFORMANCE.md); without one, that part is `needs_validation`. A headless browser does not hide a background tab: after `newTab`, `document.visibilityState` stays `visible` and no `visibilitychange` fires. When the screen relies on that event, simulate it inside the page (an `evaluate` step that overrides `visibilityState` and dispatches `visibilitychange`), and say in the check's result that the hidden state was simulated. A unit is not `blocked` for this alone; only behaviour that depends on the browser really throttling background timers stays `needs_validation`.
Example (Brasero): `usePolling` refreshes on `visibilitychange`; returning to `/admin/pedidos` must show orders that arrived while hidden, each with a single alert.

**Alerts, sounds and notifications**
Check the autoplay policy (a sound before any user gesture must not be attempted, or must fail quietly), behaviour while the tab is hidden, and the permission prompt (asked only after a user action that explains it, and a denial handled gracefully). The probe mutes audio (`muteAudio`), so audibility is never evidence; judge from source plus the visible alert that accompanies the sound, and from console errors such as a blocked `AudioContext`. A sound must never be the only signal of a new item. Toasts and banners that report arrivals do not take focus, do not cover the focused element, and, when they carry an action or information found nowhere else, follow the timing rule in `Failed mutations` [rule: UX-30, WCAG-39]. Real OS notifications and real audio output are `needs_validation`.
Example (Brasero): `src/hooks/ui/chime.ts` stays silent until the first interaction; a new order on `/admin/pedidos` must also show a visual alert, and the 15-minute late notice must appear once.

## Universal moves (they cut across every class above)

- Build a state table per surface before testing: rows loading, empty, one, error, not found, forbidden, offline, expired, restored from history; columns the personas. Fill each cell from source (file:line of the designed state, the framework convention file, or "none") and then from a capture. Gaps in the table are your units' expectations.
- Change one condition at a time (network, then session, then data, then history) and record the probe step that introduced it. When two conditions combine to cause a failure, say so in `conditions[]`.
- After every induced failure, restore the condition (`setNetwork` `fast`) and check recovery; a state that cannot be left without a full reload is part of the finding.
- Wait on conditions: `waitFor` a selector or text with a deadline, a URL for route changes, never network idle or a bare sleep as readiness [rule: E2E-01, E2E-02, E2E-03]. A `wait` step is allowed only for an interval you are measuring, and the check says so.
- When a state shows up in some runs and not others, rerun the unit alone in a fresh context three times and classify it (product race, probe wait, order dependency, data dependency, environment, external, time, unknown) as [HUNTING.md](HUNTING.md) describes. A missing loading state or a false empty that appears only under timing pressure is a product race and stays a candidate; a probe-wait or environment result goes to probe reliability [rule: E2E-14, E2E-15, E2E-16].
- Ask a consult when the decisive question belongs to another lens: whether a message is announced (ACCESSIBILITY.md), whether a slow state is a performance root cause (PERFORMANCE.md), whether a wrong figure after recovery comes from a business rule (FUNCTIONAL-FLOWS.md).

## Validation rules (checked before any finding from this file is reported)

1. Name the condition that produced the state (profile, step, session action, data state, history step) and show the probe step list that reproduces it. A state you saw once by accident, without the step that causes it, is not reproduced.
2. Show the user's view at the moment that matters with a viewport-only `screenshot` step, plus the capture's `console`, `pageErrors`, `failedRequests` or `route.status` where relevant. Full-page captures and frames mid-animation or mid-poll are not evidence of a missing state.
3. For timing claims, give the measured `feedback_ms` (or the toast lifetime), the band it missed, the profile it ran under, and whether the threshold is a quoted band or a skill threshold. A timing claim without a measurement stays `needs_validation`.
4. Check the outcome behind the message: after a failure the record must be absent (list or `count_command`), after a retry present once. A correct message over a wrong outcome is a [FUNCTIONAL-FLOWS.md](FUNCTIONAL-FLOWS.md) defect and is reported there.
5. Rule out induced side effects: a failure caused by shared infrastructure, a peer's throttle, or a server restart or rebuild (none is part of a run) is `rejected` as a fixture artifact, not reported as an app defect. An intermittent result that is not a product race is recorded under probe reliability with its class, never silently dropped [rule: E2E-16].
6. A missing framework convention file is not a finding by itself; the finding is the user-visible state it causes, shown in a capture.
7. Use `confirmed` only with a local reproduction in the stated context and promoted evidence of the user-visible state. Use `needs_validation` when the decisive fact is a real network, a deployment, rebuild or server restart, a whole-server failure, a forced server error, a real OS notification or audio output, a real device, the real server clock, or reasoning your tier could not settle, and name it in `blockers`.
